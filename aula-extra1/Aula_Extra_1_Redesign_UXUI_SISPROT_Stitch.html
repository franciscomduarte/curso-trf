Redesenhando o SISPROT: da tela atual ao protótipo gerado por IA

O SISPROT que construímos até aqui é funcional, mas o layout foi o de menor prioridade — o foco esteve em contexto, especificação e qualidade de código. Esta aula extra abre uma nova frente: usar IA também para repensar a experiência visual do sistema, em duas etapas. Na Etapa 1, enviamos as telas atuais e um briefing de design ao Google Stitch para gerar um novo protótipo. Na Etapa 2, entregamos esse protótipo e um prompt de implementação disciplinado ao Claude Code, para transformar o design em código real dentro do SISPROT — sem quebrar nenhuma regra de negócio já existente.

Regra de ouro do curso, de novo: as capturas de tela desta aula usam apenas dados fictícios (nomes, protocolos e setores inventados) — o mesmo cuidado explicado na Aula 7 vale aqui. Nunca envie uma captura de tela com dado real de cidadão a uma ferramenta de IA externa como o Stitch.

Etapa 1

Preparando o insumo: telas atuais + prompt de redesign

O primeiro passo de um redesign assistido por IA não é gerar nada — é dar ao gerador um retrato preciso do que existe hoje e uma instrução clara do que se espera como resultado.

O que é o Google Stitch

O Google Stitch é uma ferramenta experimental do Google Labs que gera telas de interface e protótipos a partir de uma descrição em texto e, opcionalmente, imagens de referência — incluindo capturas de tela de um sistema já existente. Funciona como um designer júnior que recebe um briefing bem escrito e devolve propostas visuais completas, exportáveis como imagem ou código. O acesso é feito em stitch.withgoogle.com, com login de uma conta Google, e o uso básico é gratuito.

Alternativa ao Stitch: Claude Design

A Anthropic (empresa que faz o Claude) lançou em abril de 2026 o Claude Design, um produto experimental do Anthropic Labs que também gera telas, protótipos e apresentações a partir de conversa — com um painel de chat de um lado e um canvas visual do outro, refinado por comentários ou edição direta. É acessado em claude.ai/design e roda sobre um modelo com visão (Claude Opus), o que o torna especialmente bom em interpretar as capturas de tela atuais enviadas como referência — exatamente o mesmo insumo usado com o Stitch.

A diferença prática mais importante: o Stitch é gratuito via Google Labs, enquanto o Claude Design exige um plano pago do Claude (Pro, Max, Team ou Enterprise) — não está disponível no plano gratuito. Em compensação, por ser do mesmo fabricante do Claude Code usado na Etapa 2 desta aula, o Claude Design tem integração mais direta com ele, o que pode facilitar a passagem do design para a implementação. Para usar como alternativa ao Passo 1.3: acesse claude.ai/design, anexe as duas capturas de tela atuais e cole o mesmo prompt de redesign do Passo 1.2 — a lógica de "briefing detalhado + referência visual" vale para as duas ferramentas.

Referência oficial: anthropic.com/news/claude-design-anthropic-labs · claude.com/product/design.

Passo 1.1

Reunir as telas atuais como referência

Duas capturas de tela do SISPROT em produção hoje vão servir de referência funcional para o Stitch — a listagem de protocolos e o formulário de novo protocolo. São elas que mostram todos os campos, colunas e ações que o novo design precisa preservar.

Passo 1.2

O prompt de redesign completo

Este é o briefing que acompanha as duas capturas de tela. Ele cobre identidade visual, layout, cada tela do sistema, estados de interface, acessibilidade e um pequeno design system — para que o Stitch não gere só "uma tela bonita", mas um conjunto consistente e utilizável. Copie o texto abaixo por completo.

Prompt · colar no Stitch junto com as duas capturas de tela# Redesign UX/UI — SISPROT | Sistema de Protocolo Administrativo ## Contexto Estou desenvolvendo o **SISPROT — Sistema de Protocolo Administrativo**, utilizado para cadastro, acompanhamento, tramitação e gestão de protocolos administrativos de um órgão público. As telas atuais do sistema estão funcionais, porém apresentam problemas significativos de **usabilidade, hierarquia visual, organização das informações, densidade de conteúdo e responsividade**. Utilize as telas atuais anexadas como referência funcional. **Não replique o design atual.** Quero uma proposta de redesign completa, moderna e profissional, mantendo as funcionalidades e informações existentes. O sistema deve transmitir: * confiança; * organização; * eficiência; * segurança; * institucionalidade; * simplicidade; * acessibilidade. O resultado deve parecer um **sistema administrativo profissional utilizado por um órgão público**, e não um protótipo genérico ou uma aplicação SaaS comercial. --- # 1. Diretrizes gerais de UX Redesenhe a interface seguindo princípios modernos de: * UX Design; * Design System; * Information Architecture; * acessibilidade; * responsividade; * consistência visual; * redução de carga cognitiva; * feedback visual; * prevenção de erros; * navegação intuitiva. Priorize **clareza e produtividade** em vez de excesso de elementos visuais. Evite: * excesso de bordas; * excesso de cores; * sombras exageradas; * botões pequenos; * textos muito pequenos; * tabelas espremidas; * excesso de ações simultâneas; * ícones sem significado claro; * grandes espaços vazios; * componentes visualmente desconectados. --- # 2. Identidade visual Criar uma identidade visual institucional e moderna. Utilizar como referência estética: * azul-marinho ou azul institucional para navegação e elementos principais; * tons neutros de cinza para superfícies e fundos; * branco para áreas de conteúdo; * verde/teal como cor de ação principal; * cores semânticas apenas quando realmente necessárias. IMPORTANTE: Não utilizar vermelho para representar genericamente informações negativas em escalas ou classificações. Para estados e prioridades, utilizar uma abordagem visual consistente e acessível, preferencialmente com diferentes tonalidades da mesma família cromática, complementadas por texto e/ou ícones. A interface deve funcionar também em escala de cinza. --- # 3. Layout principal Criar uma estrutura de aplicação administrativa moderna. Desktop: * cabeçalho institucional; * navegação lateral ou navegação superior claramente organizada; * área principal de conteúdo; * breadcrumb quando necessário; * título da página; * ações principais claramente destacadas. A navegação deve conter, pelo menos: * Dashboard; * Protocolos; * Novo Protocolo; * Relatórios; * Configurações. Criar uma navegação lateral recolhível no desktop. Em telas menores, transformar a navegação em menu mobile. --- # 4. Dashboard Criar uma tela inicial de dashboard do SISPROT. Apresentar indicadores resumidos: * Total de protocolos; * Protocolos abertos; * Protocolos em análise; * Protocolos deferidos; * Protocolos indeferidos; * Protocolos arquivados. Adicionar: * gráfico de protocolos por status; * gráfico de protocolos por área/setor; * protocolos recentes; * protocolos com prioridade alta; * protocolos aguardando alguma ação. Os indicadores devem ser simples, escaneáveis e não excessivamente decorativos. --- # 5. Tela "Protocolos" Redesenhar completamente a tela atual de listagem. A tela deve possuir: ### Cabeçalho Título: **Protocolos** Subtítulo curto explicando a função da página. Botão principal: **+ Novo Protocolo** ### Área de busca Criar uma barra de pesquisa ampla: **Pesquisar protocolo por número, assunto ou requerente** Adicionar filtros: * Status; * Prioridade; * Setor de origem; * Setor atual; * Período; * Área. Permitir limpar filtros. Exibir quantidade de resultados encontrados. ### Tabela A tabela deve ser muito mais legível que a atual. Colunas: * Número; * Assunto; * Requerente; * Data de abertura; * Status; * Prioridade; * Setor de origem; * Anexos; * Setor atual; * Ações. Não deixar a tabela excessivamente comprimida. Permitir: * ordenação; * paginação; * seleção de quantidade de registros; * scroll horizontal somente quando realmente necessário. As ações devem ser agrupadas em um menu de ações "..." para reduzir a poluição visual. A linha pode possuir uma ação principal: **Visualizar** E outras ações dentro do menu: * Editar; * Tramitar; * Anexar documento; * Alterar status; * Arquivar. ### Responsividade No mobile, **não simplesmente comprimir a tabela**. Transformar cada protocolo em um card/list item responsivo contendo: * número; * assunto; * requerente; * status; * prioridade; * data; * botão "Visualizar". Ao tocar no item, abrir a página de detalhes. --- # 6. Status Utilizar badges/chips claros para: * Aberto; * Em Análise; * Deferido; * Indeferido; * Arquivado. O status deve possuir: * texto; * contraste adequado; * tamanho confortável; * aparência consistente em todo o sistema. Não depender apenas da cor para comunicar o estado. --- # 7. Prioridade Representar: * Baixa; * Média; * Alta. A prioridade deve ser facilmente identificável, mas sem criar excesso de cores. Usar texto + ícone quando apropriado. --- # 8. Tela "Novo Protocolo" Redesenhar completamente a tela atual. A tela deve possuir uma estrutura clara de formulário. Cabeçalho: **Novo Protocolo** Breadcrumb: **Protocolos > Novo Protocolo** Ação secundária: **Voltar para protocolos** --- ## Formulário Organizar os campos em seções. ### Dados do protocolo Campos: * Número do protocolo — obrigatório; * Data de abertura — obrigatório; * Assunto — obrigatório; * Nome do requerente — obrigatório; * Status; * Prioridade; * Setor de origem — obrigatório; * Área. Utilizar uma grade responsiva: Desktop: 2 colunas quando fizer sentido. Mobile: 1 coluna. Não criar campos excessivamente largos quando não forem necessários. --- # 9. Validação do formulário Projetar estados visuais para: * campo obrigatório vazio; * formato inválido; * campo válido; * mensagem de erro; * mensagem de ajuda. As mensagens devem aparecer próximas ao campo. Exemplo: **Número do protocolo é obrigatório.** Evitar mensagens genéricas como: "Erro ao preencher formulário." --- # 10. Botões Criar hierarquia clara: ### Primário Salvar protocolo ### Secundário Cancelar ### Terciário Voltar O botão principal deve ser visualmente evidente. Evitar muitos botões com a mesma importância visual. --- # 11. Anexos A área atual de anexos deve ser redesenhada. Depois que o protocolo for salvo, apresentar uma seção: **Documentos e anexos** Criar uma área para: * enviar arquivo; * visualizar arquivo; * baixar arquivo; * excluir arquivo; * visualizar tamanho; * visualizar data de envio; * visualizar usuário que anexou. Criar uma área de upload intuitiva: **Arraste arquivos aqui ou clique para selecionar** Informar formatos e tamanho máximo permitidos. --- # 12. Tela "Detalhes do Protocolo" Criar uma tela específica para visualizar um protocolo. Estrutura sugerida: ### Cabeçalho Número do protocolo em destaque. Exemplo: **Protocolo nº 26/000103** Ao lado: * status; * prioridade. Ações: * Editar; * Tramitar; * Anexar documento; * Alterar status; * Mais ações. --- ## Resumo Exibir informações principais em cards ou blocos organizados: * Assunto; * Requerente; * Data de abertura; * Setor de origem; * Setor atual; * Área; * Responsável. --- # 13. Histórico de tramitação Criar uma timeline vertical. Exemplo: **13/08/2026 — Protocolo criado** Usuário: João Silva ↓ **13/08/2026 — Encaminhado para Recepção** Usuário: Maria Souza ↓ **14/08/2026 — Encaminhado para Departamento de Análise** Usuário: Carlos Santos A timeline deve permitir compreender rapidamente o caminho percorrido pelo protocolo. --- # 14. Aba de documentos Na página de detalhes, criar uma seção ou aba: **Documentos** Mostrar: * nome; * tipo; * tamanho; * data; * usuário; * ações. --- # 15. Aba de histórico Criar uma aba: **Histórico** Exibir alterações realizadas no protocolo: * criação; * edição; * alteração de status; * alteração de prioridade; * tramitação; * anexação de documento; * arquivamento. --- # 16. Experiência mobile O sistema deve ser **mobile-first e totalmente responsivo**. Criar versões para: * desktop; * tablet; * smartphone. No smartphone: * navegação adaptada; * menus em drawer; * formulários em uma coluna; * botões com área de toque adequada; * cards em vez de tabelas complexas; * ações secundárias dentro de menus; * evitar scroll horizontal sempre que possível. Não apenas redimensionar os elementos do desktop. A experiência mobile deve ser projetada especificamente para telas pequenas. --- # 17. Acessibilidade Projetar considerando WCAG. Garantir: * contraste adequado; * foco visível; * navegação por teclado; * labels associados aos campos; * mensagens de erro acessíveis; * tamanho adequado dos elementos clicáveis; * não depender somente de cores; * hierarquia correta de títulos; * textos legíveis; * estados de hover/focus/active; * suporte a leitores de tela. --- # 18. Estados da interface Desenhar também estados importantes: ### Lista * carregando; * sem resultados; * erro; * filtros aplicados; * lista normal. ### Formulário * vazio; * preenchido; * erro de validação; * salvando; * salvo com sucesso. ### Anexos * nenhum anexo; * enviando; * enviado; * erro no upload. ### Protocolo * aberto; * em análise; * deferido; * indeferido; * arquivado. --- # 19. Feedback ao usuário Criar feedback visual para operações. Exemplos: Após salvar: **Protocolo criado com sucesso.** Após alteração: **Protocolo atualizado com sucesso.** Após tramitação: **Protocolo encaminhado com sucesso.** Utilizar toast/snackbar ou mensagens contextuais discretas. Não utilizar alertas JavaScript genéricos. --- # 20. Confirmações Para ações destrutivas ou importantes, utilizar modal de confirmação. Exemplo: **Arquivar protocolo?** "Esta ação irá alterar o status do protocolo para Arquivado." Botões: **Cancelar** **Arquivar protocolo** --- # 21. Design System Criar um pequeno Design System consistente para todas as telas. Definir: * cores; * tipografia; * espaçamentos; * border radius; * sombras; * botões; * inputs; * selects; * badges; * cards; * tabelas; * modais; * dropdowns; * breadcrumbs; * tabs; * alerts; * toasts; * paginação; * estados de loading. Todos os componentes devem seguir o mesmo padrão. --- # 22. Telas que devem ser desenhadas Criar pelo menos estas telas: 1. **Dashboard** 2. **Lista de Protocolos** 3. **Novo Protocolo** 4. **Detalhes do Protocolo** 5. **Editar Protocolo** 6. **Tramitação do Protocolo** 7. **Documentos/Anexos** 8. **Histórico do Protocolo** 9. **Relatórios** 10. **Configurações** Para as principais telas, apresentar versão: * Desktop; * Mobile. --- # 23. Dados fictícios Utilizar dados realistas para demonstrar o sistema. Exemplos de assuntos: * Pedido de licença para reforma residencial; * Recurso administrativo contra multa de trânsito; * Solicitação de certidão negativa de débitos; * Solicitação de segunda via de alvará de funcionamento. Utilizar nomes fictícios. Não utilizar informações pessoais reais. --- # 24. Objetivo final O resultado deve representar uma evolução significativa das telas atuais. A nova interface deve permitir que um servidor consiga: 1. localizar rapidamente um protocolo; 2. identificar seu status; 3. identificar sua prioridade; 4. visualizar quem é o requerente; 5. saber onde o protocolo está; 6. visualizar seu histórico; 7. acessar seus documentos; 8. tramitar o protocolo; 9. alterar suas informações; 10. criar um novo protocolo com facilidade. A regra principal é: **menos poluição visual, mais hierarquia, mais clareza e mais produtividade.** Não reproduza literalmente as telas anexadas. Use-as apenas para compreender as funcionalidades, campos e informações que já existem. Crie uma proposta de **UX/UI profissional, moderna, institucional, acessível e totalmente responsiva para o SISPROT**.

Prompt longo de propósito — cada numeral (1 a 24) é uma restrição específica que evita que o Stitch devolva "uma tela genérica bonita" em vez de uma proposta usável para as 10 telas do SISPROT.

Passo 1.3

Como enviar tudo ao Stitch, na prática

  1. Acesse stitch.withgoogle.com e faça login com uma conta Google.
  2. Crie um novo projeto (botão de novo projeto / "+").
  3. Anexe as duas capturas de tela atuais — a lista de Protocolos e o formulário de Novo Protocolo — como imagens de referência.
  4. Cole o prompt completo do Passo 1.2 no campo de descrição/geração, sem cortar nenhuma seção.
  5. Gere a primeira proposta. O Stitch devolve um conjunto inicial de telas com base no briefing.
  6. Itere em cima do resultado: peça ajustes específicos em novas mensagens (ex.: "gere também a versão mobile da tela de Protocolos", "ajuste o contraste dos badges de status") até cobrir as 10 telas pedidas na seção 22 do prompt.

  • ✓As duas capturas de tela atuais anexadas como referência.
  • ✓Prompt completo (seções 1 a 24) colado sem cortes.
  • ✓Pelo menos as telas de Dashboard, Lista de Protocolos e Novo Protocolo geradas.
  • ✓Versões desktop e mobile solicitadas para as telas principais.
Por que o prompt é tão específico

Repare que o briefing não pede só "um design bonito" — ele define o que evitar (seção 1), a paleta e por que não usar vermelho para prioridade (seção 2), cada tela campo a campo (seções 4 a 15), estados de erro e sucesso (seções 9, 18 e 19) e até um mini design system (seção 21). É a mesma lógica de engenharia de prompt da Aula 4 aplicada a um domínio novo: quanto mais explícito o critério de aceitação, menos rodadas de ajuste manual depois.

O que vem depois: este passo entrega um protótipo visual, não código pronto. A Etapa 2, logo abaixo, pega o resultado gerado pelo Stitch e o traduz para o SISPROT de verdade — sempre revisando o que a IA propôs antes de aceitar.

Etapa 2

Implementação pixel-perfect com o Claude Code

O Stitch devolve imagens de um design; o SISPROT continua sendo um sistema com banco de dados, rotas, validações e regras de negócio de verdade. O segundo passo é entregar essas imagens — e um prompt igualmente disciplinado — ao Claude Code, para que o design vire código sem quebrar o que já funciona.

Por que este prompt é tão mais restritivo que o da Etapa 1

Gerar um design (Stitch) e implementar esse design dentro de um sistema já em produção (Claude Code) são tarefas com riscos muito diferentes. A primeira só produz imagens — o pior cenário é uma tela feia. A segunda mexe em código que já salva protocolos, tramita processos e valida formulários — o pior cenário é quebrar uma regra de negócio sem perceber. Por isso o prompt abaixo dedica seções inteiras a proibições explícitas (seção 19) e a preservar tudo que já funciona (seção 2), antes mesmo de falar em fidelidade visual.

Passo 2.1

O que reunir antes de rodar o prompt

  • As imagens exportadas do Stitch ao final da Etapa 1 — idealmente as 10 telas pedidas no prompt de redesign, com as versões desktop e mobile das telas principais.
  • O projeto do SISPROT aberto no editor com o Claude Code disponível (veja a Aula Extra de instalação do ambiente caso ainda falte configurar algo).
  • Um commit limpo antes de começar — sem alterações pendentes — para que cada fase da implementação possa ser revisada e revertida isoladamente, se necessário.
Passo 2.2

O prompt de implementação pixel-perfect

Este prompt acompanha as imagens geradas na Etapa 1. Ele define uma regra central — a imagem é a fonte de verdade — e, ao mesmo tempo, blinda o sistema contra o principal risco de um redesign feito por IA: alterar regra de negócio por engano. Copie o texto abaixo por completo.

Prompt · colar no Claude Code junto com as imagens exportadas do Stitch# SISPROT — Implementação Pixel-Perfect a partir dos designs do Stitch ## PAPEL Você é um **engenheiro de software sênior especializado em Front-end, UX/UI e implementação de interfaces com alta fidelidade visual**. Você está trabalhando no sistema **SISPROT — Sistema de Protocolo Administrativo**. Sua responsabilidade é implementar no sistema existente as interfaces apresentadas nas imagens de referência geradas pelo Stitch. --- # 1. REGRA PRINCIPAL — A IMAGEM É A FONTE DE VERDADE As imagens fornecidas neste prompt são os **designs oficiais da nova interface do SISPROT**. A implementação deve buscar **máxima fidelidade visual** em relação às imagens. Não faça uma interpretação livre do design. Não "melhore" o design por conta própria. Não substitua componentes por versões visualmente diferentes apenas porque são mais fáceis de implementar. Não simplifique a interface. Não crie um layout aproximado. A regra é: > **Se existe diferença visual perceptível entre a implementação e a imagem de referência, a implementação deve ser ajustada para se aproximar da referência.** Considere como elementos críticos: * posição; * dimensões; * proporções; * espaçamentos; * alinhamentos; * largura; * altura; * tipografia; * peso da fonte; * tamanho da fonte; * line-height; * cores; * bordas; * border-radius; * sombras; * ícones; * estados; * densidade da informação; * hierarquia visual; * comportamento dos componentes. --- # 2. NÃO ALTERE A REGRA DE NEGÓCIO Antes de modificar qualquer coisa, analise cuidadosamente o sistema existente. A implementação visual NÃO deve destruir ou alterar funcionalidades já existentes. Preserve: * regras de negócio; * rotas; * endpoints; * controllers; * models; * queries; * banco de dados; * validações; * autenticação; * autorização; * processamento de formulários; * upload de arquivos; * tramitação; * alteração de status; * persistência de dados. A tarefa principal é: **alterar a apresentação e a experiência de uso sem quebrar o funcionamento existente.** Se uma mudança visual exigir alteração estrutural, faça somente quando necessário e preserve o comportamento existente. --- # 3. PRIMEIRA ETAPA — ANALISAR O SISTEMA Antes de editar os arquivos, faça uma inspeção completa do projeto. Identifique: * estrutura de diretórios; * páginas existentes; * templates; * componentes; * CSS; * JavaScript; * PHP; * rotas; * controllers; * models; * arquivos de configuração; * banco de dados; * componentes reutilizáveis; * bibliotecas já utilizadas. Descubra como as telas atuais estão implementadas. Não crie uma segunda implementação paralela sem necessidade. Sempre que possível, **evolua a implementação existente**. --- # 4. IDENTIFICAR AS TELAS CORRESPONDENTES Compare as imagens fornecidas com as telas existentes no sistema. Crie mentalmente um mapeamento: | Design Stitch | Tela existente | | -------------- | ----------------------------- | | Dashboard | tela correspondente existente | | Protocolos | tela de listagem | | Novo Protocolo | formulário de cadastro | | Detalhes | tela de visualização | | Editar | formulário de edição | | Tramitação | tela de tramitação | | Documentos | área de anexos | | Histórico | histórico do protocolo | | Relatórios | tela de relatórios | | Configurações | configurações | Caso os nomes dos arquivos sejam diferentes, identifique a correspondência pela funcionalidade. --- # 5. IMPLEMENTAÇÃO VISUAL PIXEL-PERFECT Para cada tela: 1. Analise a imagem de referência. 2. Identifique a estrutura visual. 3. Identifique todos os componentes. 4. Identifique as dimensões relativas. 5. Identifique os espaçamentos. 6. Identifique a hierarquia tipográfica. 7. Identifique cores e estados. 8. Implemente. 9. Compare visualmente com a referência. 10. Corrija as diferenças. 11. Faça uma nova comparação. 12. Repita até atingir alta fidelidade. Não considere a primeira implementação como final. --- # 6. HIERARQUIA DE FIDELIDADE Ao comparar implementação e imagem, priorize nesta ordem: ### Nível 1 — Estrutura * header; * sidebar; * conteúdo; * cards; * grids; * tabelas; * formulários; * seções. ### Nível 2 — Geometria * largura; * altura; * margens; * padding; * gaps; * alinhamentos; * posicionamento. ### Nível 3 — Tipografia * família; * tamanho; * peso; * line-height; * letter-spacing; * hierarquia. ### Nível 4 — Visual * cores; * bordas; * radius; * sombras; * backgrounds; * ícones. ### Nível 5 — Microdetalhes * hover; * focus; * transições; * pequenos espaçamentos; * alinhamento de ícones; * estados de interação. --- # 7. NÃO USE "VALORES GENÉRICOS" Não faça algo como: padding: 20px; margin: 20px; font-size: 16px; simplesmente porque são valores comuns. Os valores devem ser definidos a partir da análise da referência visual. Quando necessário, utilize valores específicos para reproduzir: * dimensões; * espaçamentos; * alinhamentos; * proporções. Porém, evite transformar toda a interface em posicionamento absoluto. --- # 8. RESPONSIVIDADE A referência visual deve ser reproduzida com alta fidelidade em desktop. Porém, o sistema também deve ser verdadeiramente responsivo. Não utilize: * posições absolutas indiscriminadamente; * larguras fixas que quebrem o layout; * elementos que ultrapassem a viewport; * tabelas impossíveis de utilizar no celular; * hacks que funcionem somente em uma resolução. Utilize: * Flexbox; * CSS Grid; * unidades relativas; * max-width; * min/max; * breakpoints; * layouts fluidos. --- # 9. RESPONSIVIDADE DA TABELA DE PROTOCOLOS A tabela de protocolos é um ponto crítico. Desktop: Manter a estrutura de tabela da imagem de referência. Mobile: Não simplesmente reduzir a fonte até ficar ilegível. Transformar os registros em uma apresentação adequada para telas pequenas, por exemplo: ┌──────────────────────────┐ │ 26/000103 │ │ Pedido de licença... │ │ │ │ Molina Ilda │ │ │ │ Em Análise Média │ │ │ │ 20/02/2026 │ │ │ │ Visualizar → │ └──────────────────────────┘ A experiência mobile deve ser projetada para toque. --- # 10. FORMULÁRIOS Os formulários devem reproduzir fielmente o design. Observe: * largura dos campos; * altura; * labels; * espaçamento entre campos; * agrupamento; * mensagens de validação; * botões; * campos obrigatórios; * selects; * date pickers; * áreas de texto. Desktop: Utilizar duas colunas quando o design indicar. Mobile: Transformar em uma coluna. Não alterar os nomes dos campos ou as regras existentes sem necessidade. --- # 11. COMPONENTIZAÇÃO Sempre que houver componentes repetidos, crie componentes reutilizáveis. Exemplos: * Button; * Input; * Select; * Badge; * Card; * Modal; * Toast; * Breadcrumb; * Pagination; * Table; * Sidebar; * Header; * EmptyState; * LoadingState. Evite criar versões diferentes do mesmo componente para cada página. A aparência deve ser consistente em todo o sistema. --- # 12. DESIGN TOKENS Centralize os valores visuais recorrentes. Exemplo conceitual: :root { --color-primary: ...; --color-background: ...; --color-surface: ...; --color-border: ...; --color-text: ...; --color-text-muted: ...; --radius-sm: ...; --radius-md: ...; --radius-lg: ...; --spacing-xs: ...; --spacing-sm: ...; --spacing-md: ...; --spacing-lg: ...; --spacing-xl: ...; } Os valores devem ser definidos com base no design de referência. Não invente uma nova identidade visual diferente da apresentada pelo Stitch. --- # 13. ÍCONES Utilize a biblioteca de ícones já existente no projeto, caso exista. Se o projeto utilizar Bootstrap Icons, Font Awesome ou outra biblioteca, mantenha o padrão existente. Não misture diferentes famílias de ícones sem necessidade. Os ícones devem possuir: * tamanho adequado; * alinhamento correto; * peso visual consistente; * área de clique adequada. --- # 14. CORES Reproduza as cores da referência com a maior precisão possível. Observe especialmente: * background; * superfície; * texto principal; * texto secundário; * bordas; * botão primário; * botão secundário; * status; * prioridade; * links. Não substitua cores por nomes genéricos como: blue green gray red quando for possível obter uma aproximação muito mais precisa utilizando valores HEX/RGB/HSL. --- # 15. TIPOGRAFIA A tipografia deve receber atenção especial. Identifique na referência: * família da fonte; * tamanho; * peso; * altura da linha; * espaçamento. Se a fonte utilizada pelo design não estiver disponível, escolha a alternativa mais próxima e consistente em todo o sistema. Evite utilizar fontes diferentes em cada tela. --- # 16. ESPAÇAMENTO Um dos objetivos principais é eliminar os problemas atuais de: * excesso de espaço; * elementos comprimidos; * desalinhamentos; * campos largos demais; * tabelas apertadas. Utilize um sistema consistente de espaçamento. Observe principalmente: * distância entre título e conteúdo; * distância entre cards; * distância entre label e input; * distância entre campos; * padding interno; * espaço entre ações. --- # 17. ESTADOS DE INTERAÇÃO Além do estado normal apresentado na imagem, implemente: * hover; * focus; * active; * disabled; * loading; * success; * error; * empty. Esses estados devem seguir a mesma linguagem visual do design. --- # 18. ACESSIBILIDADE A implementação deve continuar acessível. Garantir: * labels reais; * HTML semântico; * foco visível; * navegação por teclado; * contraste adequado; * aria-label quando necessário; * mensagens de erro associadas aos campos; * botões com área de toque adequada; * não depender exclusivamente de cores. A acessibilidade não deve comprometer a fidelidade visual. --- # 19. PROIBIÇÕES NÃO: * reescrever o sistema inteiro sem necessidade; * trocar a stack existente sem autorização; * remover funcionalidades; * remover campos; * remover validações; * alterar regras de negócio; * alterar banco de dados sem necessidade; * criar dados falsos no lugar dos dados reais; * criar páginas estáticas desconectadas do backend; * usar imagens como substituição de componentes HTML; * transformar toda a interface em posições absolutas; * criar CSS duplicado desnecessariamente; * instalar bibliotecas sem necessidade; * introduzir frameworks diferentes da stack existente. --- # 20. NÃO CONFUNDA PIXEL-PERFECT COM POSICIONAMENTO ABSOLUTO Pixel-perfect significa: **alta fidelidade visual.** Não significa: **usar `position: absolute` para posicionar cada elemento.** A implementação deve continuar sendo semanticamente correta, responsiva, sustentável e funcional. --- # 21. VALIDAÇÃO VISUAL Depois de implementar cada tela, faça uma revisão visual sistemática. Compare: ### Layout * A estrutura está igual? * O conteúdo começa na mesma posição? * Os blocos possuem proporções semelhantes? ### Espaçamento * Padding está correto? * Margens estão corretas? * Os elementos estão alinhados? ### Tipografia * Tamanho semelhante? * Peso semelhante? * Line-height semelhante? ### Cores * Background correto? * Botões corretos? * Textos corretos? * Bordas corretas? ### Componentes * Botões? * Inputs? * Cards? * Badges? * Tabela? * Menus? * Ícones? ### Responsividade * Desktop correto? * Tablet correto? * Mobile correto? * Nada ultrapassa a viewport? * Não existe scroll horizontal desnecessário? --- # 22. PROCESSO DE IMPLEMENTAÇÃO Trabalhe nesta sequência: ## Fase 1 — Diagnóstico Analise o projeto e as telas existentes. Não altere código ainda. Identifique os arquivos que precisarão ser modificados. --- ## Fase 2 — Arquitetura visual Defina: * layout; * grid; * componentes; * tokens; * tipografia; * cores; * espaçamento. --- ## Fase 3 — Componentes globais Implemente primeiro: * Header; * Sidebar; * Container; * Buttons; * Inputs; * Selects; * Badges; * Cards; * Modals; * Toasts. --- ## Fase 4 — Telas Implemente as telas uma por uma, começando pela principal. Ordem sugerida: 1. Lista de Protocolos 2. Novo Protocolo 3. Detalhes do Protocolo 4. Editar Protocolo 5. Tramitação 6. Documentos 7. Histórico 8. Dashboard 9. Relatórios 10. Configurações --- ## Fase 5 — Responsividade Testar cada tela em: * 1440px; * 1280px; * 1024px; * 768px; * 480px; * 375px. Ajustar os breakpoints conforme necessário. --- ## Fase 6 — Refinamento visual Após a implementação funcional, faça uma segunda passada exclusivamente visual. Procure diferenças pequenas: * 2–4px de espaçamento; * altura de botões; * alinhamento de ícones; * tamanho de fontes; * border radius; * sombras; * largura de containers; * altura de inputs. Corrija essas diferenças. --- # 23. CRITÉRIO DE ACEITAÇÃO Considere a implementação concluída somente quando: * as telas correspondem visualmente às referências; * a hierarquia visual está correta; * os componentes possuem aparência consistente; * os espaçamentos estão coerentes; * a tipografia está próxima da referência; * as cores estão próximas da referência; * os elementos estão alinhados; * não existem elementos quebrados; * não existe overflow horizontal indevido; * o layout funciona em desktop; * o layout funciona em tablet; * o layout funciona em smartphone; * as funcionalidades existentes continuam funcionando; * formulários continuam salvando corretamente; * filtros continuam funcionando; * ações continuam funcionando; * navegação continua funcionando. --- # 24. REGRA DE OURO Sempre que precisar escolher entre: **"é mais fácil implementar assim"** e **"é mais fiel à imagem"** escolha: **"é mais fiel à imagem"**, desde que a solução continue tecnicamente correta, responsiva e sustentável. --- # 25. RESULTADO ESPERADO Quero que o SISPROT deixe de parecer uma aplicação administrativa genérica e passe a ter uma interface: * moderna; * profissional; * limpa; * institucional; * intuitiva; * consistente; * acessível; * responsiva; * visualmente sofisticada; * com alta fidelidade aos designs fornecidos pelo Stitch. As imagens anexadas são a **referência visual oficial**. Implemente o sistema buscando **pixel-perfect visual fidelity**, sem sacrificar responsividade, acessibilidade, manutenção ou as funcionalidades existentes. Comece pela análise do projeto e apresente quais arquivos/telas serão modificados antes de iniciar alterações estruturais importantes.

Note que a Fase 1 (seção 22) pede explicitamente um diagnóstico antes de qualquer alteração — é o ponto em que você revisa e aprova o plano do Claude Code antes de deixá-lo mexer em código que já está em produção.

Passo 2.3

Como rodar o prompt, fase a fase

  1. Abra o projeto do SISPROT no editor com o Claude Code disponível, com o repositório limpo (sem alterações pendentes).
  2. Anexe as imagens exportadas do Stitch na conversa, junto com o prompt completo do Passo 2.2.
  3. Deixe a Fase 1 — Diagnóstico rodar primeiro. Ela não deve alterar nenhum arquivo — só listar o que será modificado. Revise essa lista antes de autorizar qualquer mudança estrutural.
  4. Acompanhe as fases seguintes (2 a 6) uma de cada vez, revisando o diff de cada alteração antes de aceitar — a mesma disciplina de revisão de código gerado por IA já vista na Aula 6.
  5. A cada tela concluída (Fase 4), rode o sistema localmente e compare lado a lado com a imagem correspondente do Stitch.
  6. Ao final da Fase 5, teste manualmente nas resoluções indicadas no prompt (1440, 1280, 1024, 768, 480 e 375px).
  7. Antes de considerar a tela pronta, confirme que as funcionalidades existentes — salvar, filtrar, tramitar, anexar, navegar — continuam funcionando exatamente como antes.

A regra de ouro deste prompt não é sobre design

Repare que a seção 24 ("regra de ouro") deste prompt é sobre fidelidade visual, mas a seção que mais protege o sistema é a 2 ("não altere a regra de negócio") combinada com a 19 (proibições explícitas). Um redesign de UI que quebra a tramitação de um protocolo não é uma evolução — é um incidente. Trate o diff do Claude Code aqui com a mesma desconfiança produtiva da Aula 6: revisar antes de aceitar, nunca aceitar só porque "parece funcionar".

Fim das duas etapas: Etapa 1 gerou o design no Stitch; Etapa 2 o traduziu em código real no SISPROT, tela a tela, sem sacrificar as regras de negócio já existentes. O resultado esperado é o mesmo sistema, com a mesma lógica por baixo, mas com uma interface institucional, consistente e responsiva de verdade.
