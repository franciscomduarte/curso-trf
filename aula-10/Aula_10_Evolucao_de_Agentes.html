Do agente que roda numa aula ao agente que roda de verdade

Um agente de curso — como os que este material já mostrou — resolve uma tarefa e esquece tudo quando termina. Um agente de produção precisa lembrar entre sessões, se conectar a sistemas reais sem que alguém escreva uma função para cada um, dividir trabalho entre vários agentes com segurança, e alguém (ou alguma coisa) precisa conseguir dizer se ele está funcionando bem — sem reler cada resposta manualmente. Etapa 1

MCP no lugar de tools escritas à mão

A Aula 9 já explicou o que é MCP. Esta etapa mostra a diferença que isso faz na prática, no mesmo projeto do curso.

Retomando a Aula 9: MCP é um conector padrão, não um conceito novo

MCP (Model Context Protocol) é o protocolo aberto que conecta uma IA a fontes de dados e ferramentas externas — host, cliente, servidor, com tools/resources/prompts do lado do servidor. Se essa frase não soar familiar, vale revisitar a Etapa 3 da Aula 9 antes de seguir. Aqui, o ponto não é redefinir MCP — é mostrar a mudança de mentalidade que ele representa, comparado ao que o curso construiu até agora.

Exemplo real · criando e povoando um banco, inteiramente via MCP

Desta vez, "criar" não é uma página — é o próprio schema

Em vez de conectar a um banco que já existe, aqui a IA cria as tabelas e carrega os dados do zero, através da mesma conexão MCP — nenhum CREATE TABLE ou INSERT digitado à mão, nenhum script rodado fora da conversa.

Passo 0 · antes de tudo, um MySQL rodando localmente

Já instalou o XAMPP nas aulas anteriores? Só confirmar que o MySQL está ligado

Quem já monta o SISPROT em PHP + MySQL desde a Aula 4 já tem um servidor MySQL rodando em 127.0.0.1:3306, dentro do XAMPP — não precisa instalar nada de novo. Basta abrir o XAMPP Control Panel e conferir se o módulo MySQL está com o status "Running" (fundo verde); se não estiver, clicar em Start ao lado dele. Quem chegou direto nesta aula, sem XAMPP instalado, segue o passo a passo abaixo.

Instalando do zero, no Windows

XAMPP — o mesmo pacote (Apache + MySQL/MariaDB + phpMyAdmin) usado desde a Aula 4

  1. Baixar o instalador para Windows em apachefriends.org/download.html — escolher a versão mais recente com PHP 8.x.
  2. Executar o instalador. Avisos do Controle de Conta de Usuário (UAC) ou do antivírus sobre o instalador não ser assinado são esperados — o XAMPP é um pacote de código aberto sem assinatura paga; seguir mesmo assim.
  3. Na tela de seleção de componentes, manter pelo menos Apache, MySQL e phpMyAdmin marcados — os três já usados desde a Aula 4.
  4. Instalar na pasta padrão sugerida (ex.: C:\xampp) — evitar pastas com espaço no nome ou dentro de Arquivos de Programas, fonte comum de erro de permissão no MySQL.
  5. Ao concluir, abrir o XAMPP Control Panel e clicar em Start nas linhas Apache e MySQL — as duas devem ficar com fundo verde e mostrar um número de porta (MySQL, por padrão, 3306).

Confirmar que subiu: abrir localhost/phpmyadmin no navegador — a tela do phpMyAdmin abrindo sem erro de conexão é a confirmação de que o MySQL está no ar.

A senha do usuário root do XAMPP vem em branco por padrão — suficiente para os exercícios deste curso, mas não é o usuário que a IA vai usar em nenhum momento: o Passo 1, a seguir, cria um usuário dedicado (mcp_sisprot) só para essa finalidade.

Fonte: apachefriends.org — página oficial de download do XAMPP.

Passo 1 · um usuário dedicado, antes de conectar

Mesmo aqui, onde a IA vai escrever, nunca o usuário administrador

Rodar isto uma vez, manualmente, no phpMyAdmin (aba SQL) ou no cliente de linha de comando do MySQL — não faz parte do que a IA vai executar depois.

-- Rodar uma vez, manualmente — nunca via MCP CREATE DATABASE IF NOT EXISTS sisprot_mcp; CREATE USER IF NOT EXISTS 'mcp_sisprot'@'localhost' IDENTIFIED BY 'trf123456'; GRANT ALL PRIVILEGES ON sisprot_mcp.* TO 'mcp_sisprot'@'localhost'; FLUSH PRIVILEGES;

O GRANT é só em sisprot_mcp.*, nunca em *.* — mesmo precisando criar tabelas e inserir dados aqui, o usuário mcp_sisprot não enxerga nenhum outro banco do mesmo servidor. Defesa em camadas, ao contrário do que uma trava só de leitura faria: em vez de restringir a operação, restringe-se o alcance (um único banco).

Passo 2 · conectar o MySQL via MCP

Editar .mcp.json direto no projeto

O arquivo de configuração pode ser criado manualmente, na raiz do projeto, sem passar por nenhum comando claude mcp add.

// .mcp.json, na raiz do projeto (criar se não existir) { "mcpServers": { "mysql-sisprot": { "type": "stdio", "command": "npx", "args": ["-y", "@benborla29/mcp-server-mysql"], "env": { "MYSQL_HOST": "127.0.0.1", "MYSQL_PORT": "3306", "MYSQL_USER": "mcp_sisprot", "MYSQL_PASS": "trf123456", "MYSQL_DB": "sisprot_mcp", "ALLOW_INSERT_OPERATION": "true", "ALLOW_DDL_OPERATION": "true" } } } }

Mesmo formato já usado com o Copilot, no .vscode/mcp.json, ao longo do curso — só o nome do arquivo e o campo mcpServers por fora mudam. Depois de salvar: sair da sessão (/exit) e abrir de novo (claude) na mesma pasta — servidores de projeto (.mcp.json) só são detectados na inicialização, e a primeira vez pedirá aprovação explícita antes de conectar. Confirmar com claude mcp list.

ALLOW_DDL_OPERATION=true libera CREATE/DROP/ALTER; ALLOW_INSERT_OPERATION=true libera INSERT — as únicas duas permissões que este exemplo precisa. ALLOW_UPDATE_OPERATION e ALLOW_DELETE_OPERATION ficam no padrão (false) de propósito: nada aqui precisa alterar ou apagar uma linha já existente.

Alternativa por linha de comando: claude mcp add-json mysql-sisprot '{"type":"stdio","command":"npx","args":["-y","@benborla29/mcp-server-mysql"],"env":{"MYSQL_HOST":"127.0.0.1","MYSQL_PORT":"3306","MYSQL_USER":"mcp_sisprot","MYSQL_PASS":"trf123456","MYSQL_DB":"sisprot_mcp","ALLOW_INSERT_OPERATION":"true","ALLOW_DDL_OPERATION":"true"}}'.

.mcp.json fica na raiz do projeto e pode ser versionado — mas não este, com uma senha em texto puro dentro. Adicionar .mcp.json ao .gitignore antes de qualquer commit, ou trocar a senha por uma variável de ambiente do sistema operacional depois que o exercício terminar.

Fonte: pacote @benborla29/mcp-server-mysql, mantido pela comunidade — não é um produto oficial da Oracle/MySQL (github.com/benborla/mcp-server-mysql). Escrita (INSERT/UPDATE/DELETE/DDL) vem desligada por padrão — precisa ser liberada explicitamente pelas variáveis ALLOW_*, como feito acima.

Mesmo exemplo, no GitHub Copilot

Mesmo servidor MCP, arquivo de workspace em vez de .mcp.json

O agent mode do Copilot, no VS Code, conecta ao mesmo servidor @benborla29/mcp-server-mysql — muda só o arquivo (.vscode/mcp.json, não .mcp.json na raiz) e o nome do campo por fora (servers, não mcpServers), mesmo padrão já visto com o Context7 na Aula 9.

// .vscode/mcp.json (criar a pasta .vscode, se não existir) { "servers": { "mysql-sisprot": { "type": "stdio", "command": "npx", "args": ["-y", "@benborla29/mcp-server-mysql"], "env": { "MYSQL_HOST": "127.0.0.1", "MYSQL_PORT": "3306", "MYSQL_USER": "mcp_sisprot", "MYSQL_PASS": "trf123456", "MYSQL_DB": "sisprot_mcp", "ALLOW_INSERT_OPERATION": "true", "ALLOW_DDL_OPERATION": "true" } } } }
Passo a passo, no VS Code
  1. Criar a pasta .vscode na raiz do workspace (se ainda não existir), e dentro dela o arquivo mcp.json com o conteúdo acima.
  2. Com o arquivo aberto no editor, clicar no link Start que aparece acima da entrada mysql-sisprot. (Alternativa: Command Palette → MCP: List Servers → selecionar mysql-sisprot → iniciar.)
  3. Confirmar que conectou: rodar de novo MCP: List Servers na Command Palette — o servidor aparece ativo, com as tools de leitura/escrita que ele expõe.
  4. Abrir o Chat (Ctrl+Alt+I) e trocar o modo de Ask para Agent — sem isso, as tools do servidor MCP não ficam disponíveis. Configure Tools, na caixa de chat, mostra e permite ligar/desligar cada tool antes de perguntar.

.vscode/mcp.json merece o mesmo cuidado do .mcp.json: entra no .gitignore antes de qualquer commit, por causa da senha em texto puro dentro do arquivo.

Passo 4 · um segundo servidor MCP, para buscar um script antes de rodar

Notion guarda o script; MySQL executa — dois servidores MCP na mesma conversa

Cenário comum: o script de uma terceira tabela, combinado com outra área, documentado numa página do Notion — não no repositório de código. Antes de pedir para criar essa tabela, uma página de teste no Notion recebe o script mais abaixo. A IA busca esse conteúdo via MCP do Notion, e só depois executa via MCP do MySQL — dois servidores conectados na mesma sessão, cada um resolvendo sua própria parte, sem nenhuma tool escrita à mão.

// .mcp.json — Notion ao lado do mysql-sisprot já conectado no Passo 2 { "mcpServers": { "mysql-sisprot": { "type": "stdio", "command": "npx", "args": ["-y", "@benborla29/mcp-server-mysql"], "env": { "MYSQL_HOST": "127.0.0.1", "MYSQL_PORT": "3306", "MYSQL_USER": "mcp_sisprot", "MYSQL_PASS": "trf123456", "MYSQL_DB": "sisprot_mcp", "ALLOW_INSERT_OPERATION": "true", "ALLOW_DDL_OPERATION": "true" } }, "notion": { "type": "http", "url": "https://mcp.notion.com/mcp" } } }

Diferente do mysql-sisprot (stdio, local), o Notion é um servidor remoto (HTTP) com OAuth — a primeira conexão pede autorização no navegador, dentro da própria sessão do Claude Code (rodar /mcp e seguir o fluxo). Alternativa por linha de comando: claude mcp add --transport http notion https://mcp.notion.com/mcp — o mesmo comando do Exercício 1 da "Mão na massa", mais adiante; usar um workspace de teste, nunca um com dado real do órgão.

Fonte: documentação oficial da Notion sobre MCP (developers.notion.com/guides/mcp/get-started-with-mcp) — o servidor remoto usado acima é o caminho que a própria Notion recomenda hoje; existe também uma versão local, de código aberto (github.com/makenotion/notion-mcp-server).

Antes de pedir à IA · colar isto numa página de teste do Notion

O script da terceira tabela, guardado fora do repositório de código

-- Colar como texto/código numa página do Notion, ex.: "Script SISPROT — tabela movimentacoes" CREATE TABLE movimentacoes ( id INT AUTO_INCREMENT PRIMARY KEY, protocolo_id INT NOT NULL, status_anterior ENUM('Em Análise','Deferido','Indeferido','Arquivado') NULL, status_novo ENUM('Em Análise','Deferido','Indeferido','Arquivado') NOT NULL, data_movimentacao DATE NOT NULL, observacao VARCHAR(200) NULL, FOREIGN KEY (protocolo_id) REFERENCES protocolos(id) ); INSERT INTO movimentacoes (protocolo_id, status_anterior, status_novo, data_movimentacao, observacao) VALUES (1, NULL, 'Em Análise', '2026-01-12', 'Protocolo aberto'), (1, 'Em Análise', 'Deferido', '2026-01-20', 'Aprovado pelo setor de Protocolo Geral'), (5, NULL, 'Em Análise', '2026-02-05', 'Protocolo aberto'), (5, 'Em Análise', 'Indeferido', '2026-02-12', 'Recurso negado'), (7, NULL, 'Em Análise', '2025-11-30', 'Protocolo aberto'), (7, 'Em Análise', 'Arquivado', '2025-12-10', 'Arquivado por falta de manifestação');

movimentacoes referencia protocolos já existentes pelo id (1, 5 e 7 — os mesmos protocolos "Deferido", "Indeferido" e "Arquivado" carregados no Passo 3) — por isso só pode ser criada depois das duas tabelas anteriores, nunca antes.

Prompt · buscar no Notion, executar no MySQL — os dois MCP na mesma instruçãoBusque, na página de teste do Notion chamada "Script SISPROT — tabela movimentacoes", o script SQL que colei lá. Depois, usando a conexão MySQL (mysql-sisprot), execute esse script exatamente como está — crie a tabela e carregue os dados. Se a tabela movimentacoes já existir, pare e me avise antes de qualquer alteração.

Mesmo cuidado de sempre — "pare e me avise" antes de qualquer CREATE — mas agora testando também a ponte entre os dois servidores: a IA precisa buscar corretamente o texto de um (Notion) antes de agir com o outro (MySQL), sem misturar conteúdo de um servidor com o comando do outro.

Prompt · conferir o resultado, cruzando as duas tabelasQuais protocolos tiveram uma movimentação de "Em Análise" para "Indeferido"? Traga o número do protocolo, o assunto e a data da movimentação.

Resposta esperada com os dados de exemplo: só o protocolo 2026.005 ("Recurso administrativo"), em 2026-02-12 — o único, entre os três eventos carregados em movimentacoes, com esse status final.

Não é "MCP sempre substitui tool manual"

Para uma regra de negócio muito específica do próprio órgão (ex.: a lógica exata de quando um protocolo pode ser arquivado no SISPROT), escrever a tool à mão continua fazendo sentido — não existe (nem faria sentido existir) um servidor MCP genérico para uma regra interna específica. MCP compensa quando a capacidade já é um problema resolvido por alguém de fora (ler um banco, mexer no Notion, abrir uma issue no GitHub) — não quando é a lógica que só o próprio órgão sabe.

Passo 5 · um terceiro servidor MCP, para virar gráfico o que a consulta devolveu

MySQL responde a pergunta; um servidor de gráficos desenha o resultado — sem escrever uma linha de código de visualização

Mesma lógica dos Passos 2 e 4: em vez de pedir para a IA escrever código de gráfico (matplotlib, Chart.js, o que for), conecta-se um servidor MCP que já sabe desenhar — a IA só decide qual tipo de gráfico faz sentido para a pergunta e monta a chamada com os dados que o mysql-sisprot acabou de devolver.

// .mcp.json — mcp-server-chart ao lado do mysql-sisprot e do notion já conectados { "mcpServers": { "mysql-sisprot": { "type": "stdio", "command": "npx", "args": ["-y", "@benborla29/mcp-server-mysql"], "env": { "MYSQL_HOST": "127.0.0.1", "MYSQL_PORT": "3306", "MYSQL_USER": "mcp_sisprot", "MYSQL_PASS": "trf123456", "MYSQL_DB": "sisprot_mcp", "ALLOW_INSERT_OPERATION": "true", "ALLOW_DDL_OPERATION": "true" } }, "notion": { "type": "http", "url": "https://mcp.notion.com/mcp" }, "mcp-server-chart": { "type": "stdio", "command": "npx", "args": ["-y", "@antv/mcp-server-chart"] } } }

Alternativa por linha de comando: claude mcp add-json mcp-server-chart '{"type":"stdio","command":"npx","args":["-y","@antv/mcp-server-chart"]}'. Nenhuma chave de API é necessária — só o Node/npx já usado pelos outros servidores stdio deste exercício.

Fonte: pacote @antv/mcp-server-chart, projeto oficial da AntV (github.com/antvis/mcp-server-chart) — diferente do MySQL da comunidade, este é mantido pelo próprio time que criou a biblioteca de gráficos.

Mesmo exemplo, no GitHub Copilot

Mesmo servidor de gráficos, no arquivo de workspace

Igual aos Passos 2 e 4: muda só o arquivo (.vscode/mcp.json, não .mcp.json) e o nome do campo por fora (servers, não mcpServers).

// .vscode/mcp.json { "servers": { "mysql-sisprot": { "type": "stdio", "command": "npx", "args": ["-y", "@benborla29/mcp-server-mysql"], "env": { "MYSQL_HOST": "127.0.0.1", "MYSQL_PORT": "3306", "MYSQL_USER": "mcp_sisprot", "MYSQL_PASS": "trf123456", "MYSQL_DB": "sisprot_mcp", "ALLOW_INSERT_OPERATION": "true", "ALLOW_DDL_OPERATION": "true" } }, "mcp-server-chart": { "type": "stdio", "command": "npx", "args": ["-y", "@antv/mcp-server-chart"] } } }

Por padrão, os dados do gráfico saem da sua máquina. Sem configuração extra, o mcp-server-chart envia a especificação do gráfico — incluindo os valores — para um serviço hospedado pela AntV (antv-studio.alipay.com), que desenha a imagem e devolve o link. Para o dado fictício deste exercício, tudo bem; com dado real e sensível do órgão, isso violaria a regra de ouro do curso. Alternativa: apontar a variável de ambiente VIS_REQUEST_SERVER para uma instância própria do renderizador (projeto GPT-Vis-SSR, da própria AntV), hospedada dentro do órgão.

Prompt · consulta e gráfico, encadeando dois servidores MCP na mesma instruçãoUsando a conexão MySQL (mysql-sisprot), consulte quantos protocolos existem em cada status. Depois, usando o servidor de gráficos (mcp-server-chart), gere um gráfico de barras com esse resultado — um status por barra, ordenado do maior para o menor total.

O servidor expõe uma tool por tipo de gráfico — generate_bar_chart, generate_pie_chart, generate_line_chart, entre outras 26 no total — a IA escolhe a tool certa a partir do pedido, sem precisar que ninguém decida isso por ela.

Com isso, a Etapa 1 fecha o ciclo completo: um servidor MCP para ler/gravar dado estruturado (mysql-sisprot), um para buscar conteúdo fora do repositório (notion) e um para transformar resultado em imagem (mcp-server-chart) — três capacidades prontas, encadeadas na mesma conversa, sem uma linha de tool escrita à mão.

Pratique · individual · 10 perguntas

Encadeando os servidores da Etapa 1, na base já montada

Para cada pergunta, peça a resposta usando a conexão MySQL (mysql-sisprot) e decida se também vale a pena pedir um gráfico, encadeando o mcp-server-chart como no Passo 5 — nem toda pergunta pede um gráfico, mas várias abaixo se prestam bem a um.

  1. Quantos protocolos existem em cada status? (boa candidata a gráfico de barras)
  2. Quantos protocolos cada setor tem, ao todo? (boa candidata a gráfico de barras ou pizza)
  3. Quais protocolos do setor Jurídico ainda estão "Em Análise"?
  4. Qual setor tem mais protocolos indeferidos?
  5. Quantos dias, em média, um protocolo levou entre a abertura e o fechamento, considerando só os que já têm data_fechamento?
  6. Quantos protocolos foram abertos em cada mês de 2026? (boa candidata a gráfico de linha)
  7. Qual é o protocolo "Em Análise" há mais tempo, contando a partir da data_abertura?
  8. Quantas movimentações cada protocolo registrado em movimentacoes teve, do mais para o menos movimentado?
  9. Quais protocolos mudaram de "Em Análise" direto para "Indeferido", e quantos dias essa mudança levou?
  10. Qual a proporção de protocolos "Deferido" em cada setor? (boa candidata a um gráfico de pizza por setor)

Nenhuma dessas dez precisa de uma tool nova — os dois servidores já conectados nesta etapa (mysql-sisprot e mcp-server-chart) bastam para todas, inclusive a 8ª e a 9ª, que cruzam protocolos com movimentacoes.

Exercício rápido · individual · 5 min

Tool escrita à mão, ou servidor MCP pronto? — usando o exemplo setores/protocolos da Etapa 1

Para cada capacidade abaixo, decida se faz mais sentido escrever uma tool própria (T) ou conectar um servidor MCP já existente (M) — todas ligadas ao mesmo banco sisprot_mcp conectado via mysql-sisprot na Etapa 1. A sequência correta das 6 respostas é a senha que libera o gabarito.

T = tool escrita à mão  ·  M = servidor MCP pronto
  1. Consultar quantos protocolos existem em cada status, direto no banco sisprot_mcp.
  2. Criar as tabelas setores e protocolos, e carregar a base inicial de dados.
  3. Descobrir as colunas e os tipos de cada tabela do banco antes de montar uma consulta nova.
  4. A regra específica de quando um protocolo do SISPROT pode mudar de "Em Análise" para "Deferido".
  5. Calcular, com a fórmula exata usada só neste órgão, o prazo final de um processo administrativo.
  6. Montar e enviar, no modelo de e-mail específico deste tribunal, a cobrança ao responsável por um protocolo parado há mais de 30 dias.

1, 2 e 3 são capacidades genéricas de acesso a um banco MySQL — ler dados, criar schema e carregar registros, inspecionar colunas — já resolvidas pelo servidor mysql-sisprot conectado na Etapa 1; não faz sentido reescrever isso à mão. 4, 5 e 6 são regras e formatos específicos deste órgão, que nenhum servidor de terceiro poderia conhecer — continuam sendo tool escrita à mão, do mesmo jeito que em agentes/tools.py.

Etapa 2

Multiagentes de verdade

A aula anterior desenhou o diagrama de um orquestrador, mas nunca implementou. Esta etapa detalha as opções reais, reaproveitando os servidores MCP já conectados na Etapa 1.

Três formas diferentes de "mais de um agente", não uma só

"Multiagente" é um termo guarda-chuva — na prática, existem pelo menos três padrões distintos, cada um resolvendo um problema diferente. A Aula 9 (Etapa 2) já apresentou o primeiro; aqui os três, lado a lado.

PadrãoComo funcionaQuando usar
SubagenteDentro da mesma sessão — a conversa principal delega, espera o resultado, e continua.Uma tarefa geraria muito conteúdo descartável (logs, buscas) que não deveria poluir o histórico principal.
Agent teamsVárias sessões paralelas, uma coordenando as outras, cada uma com contexto próprio — recurso ainda experimental no Claude Code.Trabalho divisível em partes independentes, revisadas depois por quem coordena.
Multiagentes especializados e independentesAgentes completos e separados (como o de migração e o de análise deste curso), cada um com seu próprio papel, coordenados por um terceiro — o orquestrador.Domínios diferentes o bastante para merecerem instruções, ferramentas e restrições completamente separadas.

O mesmo diagrama já esboçado na aula anterior — aqui, o "ORQUESTRADOR" é o terceiro padrão da tabela acima: um agente (ou uma peça de código simples) que decide "essa tarefa é de migração" ou "essa tarefa é de análise", e encaminha para o especialista certo.

O orquestrador nem sempre precisa ser um agente de IA

Uma armadilha comum: assumir que decidir "qual agente chamar" também precisa de um modelo de IA. Às vezes um roteamento simples (palavra-chave no pedido, um menu de opções, uma regra de negócio) resolve com mais previsibilidade e menos custo do que colocar mais uma chamada de IA só para decidir para onde mandar a tarefa. Vale perguntar, antes de automatizar a decisão com IA: essa escolha é ambígua o bastante para precisar de julgamento, ou é sempre óbvia a partir do pedido?

Exemplo real · dois agentes, duas conexões MCP já conectadas na Etapa 1

Multiagente com MCP não é só teoria — é a forma natural de dividir permissão

Reaproveitando os dois servidores já conectados e testados na Etapa 1 desta aula (mysql-sisprot e mcp-server-chart): um agente especializado só consulta o banco sisprot_mcp (nunca desenha nada), outro especializado só transforma um resultado em gráfico (nunca toca no banco), e um orquestrador encaminha a tarefa entre os dois — exatamente o terceiro padrão da tabela acima, agora sobre a mesma base de protocolos e setores já montada, não bancos fictícios novos.

# Claude Code — .claude/agents/consultor-sisprot.md --- name: consultor-sisprot description: Só consulta o banco sisprot_mcp (protocolos, setores, movimentacoes) via MCP — nunca desenha gráfico nem altera dado tools: mcp__mysql-sisprot --- Você só lê dados do banco sisprot_mcp, através do servidor MCP conectado. Nunca tente gerar imagem nem alterar nenhum registro — sua única função é trazer o resultado da consulta pedida. # Claude Code — .claude/agents/gerador-grafico.md --- name: gerador-grafico description: Só transforma um resultado já pronto em gráfico via MCP — nunca consulta banco nem qualquer outra fonte tools: mcp__mcp-server-chart --- Você só transforma em gráfico o resultado que já chegou pronto, através do servidor MCP conectado. Nunca tente consultar um banco ou buscar dado em outro lugar — essa parte é sempre de outro agente.

Mesmo formato dos subagentes da Aula 9 (Etapa 2) — cabeçalho YAML mais prompt de sistema. A diferença é o campo tools: em vez de Read, Grep, cada um recebe só o prefixo do servidor MCP que precisa (mcp__mysql-sisprot ou mcp__mcp-server-chart) — a mesma convenção "mcp__<servidor> libera todas as ferramentas daquele servidor" já explicada na Aula 9. Isso é o que garante, na prática, que o agente do gráfico nunca consiga ler o banco, e vice-versa.

Passo a passo para montar o orquestrador
  1. Ter os dois servidores MCP já conectados na sessão (mysql-sisprot e mcp-server-chart, Passos 2 e 5 da Etapa 1) — confirmar com claude mcp list.
  2. Salvar os dois arquivos acima em .claude/agents/, dentro do projeto.
  3. Não é preciso criar um terceiro arquivo "orquestrador" — a própria sessão principal do Claude Code faz esse papel: ela lê o pedido, casa cada parte com a description do subagente certo (o mesmo casamento automático já visto na Aula 9), e decide a ordem sozinha.
  4. Pedir a tarefa completa, numa sessão comum do Claude Code, na pasta do projeto — o prompt abaixo.
Prompt dado ao orquestradorQuantos protocolos existem em cada status na base sisprot_mcp? Gere um gráfico de barras com esse resultado, um status por barra, ordenado do maior para o menor total.

O orquestrador decide, nessa ordem: primeiro aciona o agente com acesso ao mysql-sisprot (traz a contagem por status), depois passa o resultado para o agente com acesso ao mcp-server-chart (transforma em imagem) — cada um só com a permissão que precisa para sua parte, nunca as duas conexões no mesmo agente. Vale perguntar, depois: "qual agente você usou para cada parte?" — a mesma checagem de transparência da Aula 9. É a mesma pergunta já respondida na Etapa 1 — lá, numa única sessão sem separação; aqui, a diferença é a fronteira de permissão: nenhum agente enxerga a ferramenta que não usa.

Etapa 3

Observabilidade

Os logs `[AGENTE]`/`[TOOL]`/`[RESULTADO]` da aula anterior eram para uma pessoa acompanhar ao vivo. Produção precisa de outra coisa.

Definição: observabilidade de agente

A capacidade de responder, depois do fato, "o que esse agente fez, quanto custou, e onde exatamente deu errado" — sem precisar ter estado olhando o terminal no momento. Os logs impressos no terminal da aula anterior são bons para uma demonstração ao vivo; não servem para um agente rodando em produção, sem ninguém olhando a tela o tempo todo.

SinalO que registra
LogsEventos discretos, com timestamp — "tool X chamada às 14:32:07, com estes argumentos".
MétricasNúmeros agregados ao longo do tempo — quantas tools por execução, custo médio em tokens, taxa de erro por dia.
Traces (rastreamento)A cadeia completa de uma execução — cada chamada ao modelo e cada tool viram um "span" dentro do mesmo traço, permitindo reconstruir a sequência inteira depois.
Já existe um padrão aberto para isso: OpenTelemetry GenAI

A OpenTelemetry — já um padrão estabelecido para observabilidade de sistemas em geral — formou um grupo de trabalho específico para IA generativa, com convenções semânticas cobrindo chamadas de LLM, spans de agente, chamadas de tool (incluindo tools via MCP), e eventos de conteúdo (prompt/resposta). A vantagem de um padrão aberto: instrumentação automática já existe para OpenAI, Anthropic, LangChain e LlamaIndex, e ferramentas de observabilidade (Datadog, New Relic, Dynatrace, entre outras) já leem esse formato nativamente — não é preciso inventar um formato de log próprio para cada projeto.

# O que um span de tool, no padrão OpenTelemetry GenAI, registra (conceitual) — sobre a própria consulta da Etapa 1 span: "mysql_query" gen_ai.operation.name: "execute_tool" gen_ai.tool.name: "mcp__mysql-sisprot__mysql_query" gen_ai.tool.call.arguments: {"sql": "SELECT status, COUNT(*) AS total FROM protocolos GROUP BY status ORDER BY total DESC"} gen_ai.tool.call.result: [{"status":"Deferido","total":4}, {"status":"Em Análise","total":3}, {"status":"Indeferido","total":2}, {"status":"Arquivado","total":1}] duration_ms: 2 # -- e esse span vive dentro do span maior da execução do agente inteira, ao lado do span seguinte (mcp__mcp-server-chart__generate_bar_chart)

Não é um formato deste curso — é a convenção real que existe hoje para isso, resumida aqui de forma simplificada. Os valores acima são os mesmos que saíram da consulta real da Etapa 1, não um exemplo hipotético.

Amarra direto com a Etapa 6 da Aula 9

A Aula 9 já tratou logs visíveis como parte de segurança/auditoria — "toda tool chamada aparece no terminal, com parâmetros e resultado". Observabilidade é a versão dessa mesma ideia, pronta para um sistema que roda sem ninguém olhando: os mesmos três dados (ação, parâmetros, resultado) viram sinal estruturado, buscável, e alarmável — não texto solto num terminal que ninguém vai reler.

Exercício rápido · individual · 5 min

Log, métrica ou trace?

A sequência correta das 6 respostas é a senha que libera o gabarito.

L = log  ·  M = métrica  ·  T = trace
  1. "A tool mysql_query foi chamada às 14:32:07, com este SQL exato: SELECT status, COUNT(*) FROM protocolos GROUP BY status."
  2. "Nas últimas 24 horas, o custo médio por execução foi de 1.200 tokens."
  3. "A execução completa da tarefa 'protocolos por status': primeiro mysql_query, depois generate_bar_chart, até a conclusão, em ordem."
  4. "A taxa de erro desta semana foi de 3%."
  5. "Em 18/08, às 09:15:02, o agente recebeu o pedido 'quantos protocolos existem em cada status?'."
  6. "Reconstruir, depois do fato, todos os passos da execução que gerou o gráfico de barras da Etapa 1."

1 e 5 são eventos discretos, com timestamp — logs. 2 e 4 são números agregados ao longo do tempo — métricas. 3 e 6 são a cadeia completa de uma execução, reconstruída depois — traces. Repare que "reconstruir o que aconteceu numa execução específica" é sempre trace, mesmo quando a pergunta não usa a palavra "sequência" explicitamente.

Etapa 4

Avaliação automática

Como saber se um agente está bom, sem uma pessoa relendo cada resposta.

Definição: LLM-as-a-Judge

Usar um modelo de IA para julgar a resposta de outro modelo (ou do próprio agente) — comparando com um critério, uma resposta de referência, ou uma rubrica. Não é ficção especulativa: já é prática estabelecida, com estudos mostrando um juiz de IA concordando com avaliadores humanos cerca de 85% das vezes — uma taxa mais alta do que dois avaliadores humanos costumam concordar entre si na mesma tarefa. Pedir ao modelo-juiz para explicar o raciocínio antes de dar a nota (o mesmo princípio de "mostrar o processo" já visto no curso) melhora a confiabilidade do julgamento em 10 a 15%, segundo a mesma pesquisa.

AbordagemO que avalia
LLM-as-a-Judge (clássico)Só a resposta final — "essa resposta responde bem à pergunta, comparada com o esperado?"
Agent-as-a-JudgeO caminho inteiro — quais tools o agente chamou, em que ordem, com quais argumentos, não só o texto final. Mais caro, mais completo.
Avaliação multiagente (debate/colaboração)Vários juízes de IA avaliando em conjunto, depois sintetizando um veredito — reduz o viés de um único juiz.

Fonte: pesquisa e comparativos de avaliação automática de LLM/agentes, 2026.

Aplicado ao nosso exemplo

Como isso avaliaria a tarefa "protocolos por status" da Etapa 1

Um "Agent-as-a-Judge" para aquela tarefa não perguntaria só "o gráfico final ficou bom?" — perguntaria também: o agente consultou de verdade o banco sisprot_mcp via mysql-sisprot, ou os números vieram inventados? A contagem bate com um SELECT status, COUNT(*) rodado à parte, como referência? A tool de gráfico escolhida foi generate_bar_chart, como pedido, e não outra? Essas perguntas viram uma rubrica automatizável, rodada logo depois da execução — sem ninguém reabrindo o histórico da conversa manualmente toda vez.

Prompt · pedindo a um segundo agente para julgar a execução da Etapa 1Você é um avaliador. Abaixo está a pergunta original, as tools que o agente chamou (com parâmetros e resultado de cada uma) e o gráfico que ele gerou. Compare com este resultado de referência, rodado à parte: SELECT status, COUNT(*) FROM protocolos GROUP BY status ORDER BY COUNT(*) DESC. Dê nota de 1 a 5 para cada critério, com justificativa: 1. A contagem por status bate com o resultado de referência? 2. O agente consultou o mysql-sisprot de verdade, ou os números parecem inventados? 3. A tool de gráfico usada foi generate_bar_chart, e não outro tipo? 4. O gráfico saiu ordenado do maior para o menor, como pedido?
// Exemplo de veredito devolvido pelo juiz — rodado sobre a execução real da Etapa 1 1. Contagem: 5/5 — Deferido=4, Em Análise=3, Indeferido=2, Arquivado=1, idêntico ao SELECT de referência. 2. Consulta real: 5/5 — o histórico mostra mysql_query executado antes da resposta, não um número solto no texto. 3. Tool certa: 5/5 — generate_bar_chart foi a tool chamada, não generate_pie_chart nem generate_line_chart. 4. Ordenação: 5/5 — Deferido (4) primeiro, Arquivado (1) por último. Nota final: 5/5 — nenhum critério falhou.

Isso não é hipotético — é o mesmo prompt que dá para rodar agora, colando o histórico real da sua própria execução da Etapa 1 no lugar de "abaixo está..." — o juiz é só mais uma chamada de IA, sem infraestrutura nova. Se a contagem ou a tool escolhida não baterem, o veredito reprova o critério específico, não a tarefa inteira — é isso que separa uma nota única de uma rubrica.

Um avaliador de IA também pode errar — e precisa da mesma desconfiança

85% de concordância com humanos é alto, não é 100%. Um "juiz" de IA carrega os mesmos riscos já ensinados no curso inteiro: pode alucinar um critério que não existe, pode ter viés sistemático a favor de respostas mais longas ou mais confiantes. Avaliação automática reduz o trabalho de revisar cada resposta manualmente — não elimina a necessidade de, de vez em quando, auditar o próprio avaliador.

Exercício rápido · individual · 5 min

Isso é avaliação de resposta final, ou do caminho inteiro?

A sequência correta das 6 respostas é a senha que libera o gabarito.

R = avalia só a resposta final  ·  C = avalia o caminho/processo inteiro
  1. "A contagem de protocolos por status no gráfico final bate com o SELECT ... GROUP BY status de referência?"
  2. "O agente consultou o mysql-sisprot de verdade, ou os números parecem inventados?"
  3. "O gráfico gerado está ordenado do maior para o menor, como pedido?"
  4. "Em algum momento da execução, o agente tentou um INSERT ou UPDATE na base sisprot_mcp, mesmo sem ter sido pedido?"
  5. "A legenda e os rótulos do gráfico estão bem formatados e legíveis?"
  6. "Qual tool de gráfico o agente escolheu — generate_bar_chart ou outra — e isso bateu com o pedido de 'gráfico de barras'?"

1, 3 e 5 avaliam só o que saiu no final, sem olhar como se chegou lá — LLM-as-a-Judge clássico. 2, 4 e 6 exigem olhar a sequência de ações tomadas (qual tool rodou, se tentou escrever, qual tool de gráfico foi escolhida), não só o resultado — é exatamente o que separa Agent-as-a-Judge de uma avaliação tradicional.

Etapa 5

Memória entre sessões

Todo agente que este curso construiu esquecia tudo assim que o processo terminava. Esta é a última lacuna.

Definição: memória entre sessões

A capacidade de um agente guardar informação relevante depois que uma execução termina, e recuperar essa informação numa execução futura — sem que o usuário precise repetir tudo. O padrão de 2026: memória é tratada como uma camada de arquitetura separada da janela de contexto do modelo, não como "só mais histórico de chat colado no prompt". Durante uma conversa, essa camada extrai fatos relevantes e guarda; no início de uma sessão nova, busca o que for relevante (por similaridade, palavra-chave, ou entidade) e injeta de volta no contexto, antes do modelo responder.

Tipo de memóriaO que guarda
EpisódicaEventos específicos, em ordem — "na sessão de terça, o usuário aprovou a migração dos departamentos, mas recusou a de movimentações".
SemânticaConhecimento generalizado, não a conversa específica — "este usuário prefere que eu sempre proponha o SQL antes de perguntar, não pergunte antes de ter uma proposta pronta".
Um exemplo real, rodando agora — não é hipotético

A própria ferramenta usada para preparar este curso tem um sistema de memória: arquivos de texto simples, um por assunto, guardados numa pasta que persiste entre conversas diferentes — sem banco vetorial, sem serviço externo. No início de uma conversa nova, a ferramenta decide se algum desses arquivos é relevante e lê antes de responder; ao longo da conversa, decide se algo que acabou de acontecer merece virar um arquivo novo. É uma implementação real do padrão "memória baseada em arquivo" citado como abordagem válida na pesquisa sobre o tema — não a única forma de fazer, mas prova de que a ideia funciona sem infraestrutura pesada.

AbordagemQuando faz sentido
Arquivos (Markdown/texto), lidos e escritos pelo próprio agentePoucos usuários, memória por pessoa ou por projeto, sem precisar buscar por similaridade em milhares de fatos.
Banco vetorial (Pinecone, Qdrant, Milvus) indexado por usuário/sessãoMuitos fatos acumulados, precisa buscar "o que é parecido com isto" em vez de "o que eu sei sobre X".
Serviço gerenciado de memória (Mem0, Zep, e outros)Não quer operar a infraestrutura de busca — paga por isso como serviço, plugado ao agente.

Fonte: levantamento de soluções e arquiteturas de memória de agente, 2026 (pesquisa de mercado, sem um único padrão dominante — a escolha depende do volume e da necessidade de busca por similaridade).

O mesmo raciocínio de custo e risco das aulas anteriores, aplicado à memória

Memória que cresce sem limite eventualmente também cresce em custo (mais contexto injetado, mais tokens a cada chamada — o mesmo problema de custo por token da Aula 7) e em risco (se o agente guarda dado sensível "porque foi mencionado uma vez", isso agora persiste além da sessão que o gerou — o mesmo cuidado de minimização e anonimização da Aula 7, agora aplicado a um sistema que lembra por padrão, não que esquece por padrão).

Exercício rápido · individual · 5 min

Esse caso precisa de memória entre sessões?

Para cada situação abaixo, decida se o agente realmente precisa lembrar de uma sessão anterior (M) ou se cada execução pode continuar começando do zero, sem perda real (S — sem memória, está bom assim). A sequência correta das 6 respostas é a senha que libera o gabarito.

M = precisa de memória entre sessões  ·  S = sem memória, tudo bem
  1. Um agente que analisa um único relatório fechado, uma vez, e entrega o resultado.
  2. Um agente de atendimento que deveria lembrar que, na semana passada, o mesmo servidor já relatou o mesmo problema.
  3. Um agente que converte um arquivo CSV num formato novo, tarefa isolada, sem relação com execuções anteriores.
  4. Um agente de migração que deveria lembrar quais tabelas um humano já aprovou, para não perguntar de novo a cada nova sessão.
  5. Um agente que só responde "qual a capital deste estado", uma pergunta e pronto.
  6. Um assistente que deveria lembrar que um usuário específico sempre prefere respostas mais curtas, em qualquer conversa futura.

1, 3 e 5 são tarefas isoladas e completas em si mesmas — nada se perde recomeçando do zero a cada vez. 2 e 4 são memória episódica (lembrar um evento específico de antes); 6 é memória semântica (uma preferência geral, não um evento) — os três precisam de memória entre sessões para funcionar como descrito.

Repetir o padrão dos dois exercícios anteriores, mas sem passo a passo — com um servidor à escolha.

Escolheremos um terceiro servidor MCP à escolha — GitHub, Google Drive, Slack, um servidor de sistema de arquivos local, ou qualquer outro que o Claude Code suporte — e repetiremos o ciclo: conectar, autorizar, testar uma pergunta real, documentar.

Regras
  1. Antes de conectar, verificar se o servidor escolhido está ativamente mantido — o mesmo cuidado já ensinado na Aula 9, ao instalar uma skill ou conectar um servidor MCP qualquer.
  2. Documentar, em texto curto: qual servidor, quais tools ele expôs (peça à IA para listar), e uma pergunta real que só funcionou depois da conexão.
  3. Nenhum dado real e sensível do órgão em nenhuma conexão — usar conta, workspace, repositório ou banco de teste.
Critério de sucesso
  • ✓O servidor conectou de verdade — claude mcp list mostra ele ativo.
  • ✓Conseguimos listar, com as palavras da própria IA, quais tools esse servidor específico expôs.
  • ✓Verificamos o status de manutenção do servidor antes de conectar, não depois.

Uma tarefa, todas as camadas

Prompt · conduzido ao vivo, com mysql-sisprot, mcp-server-chart e Notion conectadosConsulte quantos protocolos cada setor tem, no banco sisprot_mcp conectado. Gere um gráfico com esse resultado. Nomear, em voz alta, cada camada que aparece: um objetivo (Aula 9/10), decisão de qual tool usar entre duas fontes diferentes (Etapa 1/2 desta aula), MCP como o conector real (Aula 9, Etapa 3-4), e — se sobrar tempo — perguntar "como eu saberia se essa resposta foi boa?" para amarrar com a Etapa 4.

Fechando o curso

Da Aula 0 — um prompt bem escrito, sem IA agindo sozinha — até aqui — uma IA que decide, age através de ferramentas reais, e (com as cinco peças desta aula) pode lembrar, ser observada e ser avaliada sem alguém checando cada resposta — a pergunta central nunca mudou: como confiar no que a IA produz, sem deixar de decidir por conta própria. As ferramentas específicas vão continuar mudando depois deste curso; essa pergunta, não.

Dez aulas atrás, a pergunta era como escrever um prompt melhor. Hoje, é como confiar — com evidência, não com fé — num sistema que decide, age, lembra e se conecta a ferramentas reais por conta própria. A tecnologia por trás vai mudar; a disciplina de medir, verificar e manter uma pessoa no controle das decisões que importam não deveria.
