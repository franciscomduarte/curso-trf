Etapa 1

O ciclo Spec-Driven Development

Especificar antes de pedir não é uma etapa extra — é o que faz o prompt possível de escrever bem.

Definição: Spec-Driven Development

É a prática de descrever, numa especificação estruturada, o que o sistema deve fazer antes de pedir para a IA implementar — fechando o ciclo requisito → spec → prompt → código → verificação contra os critérios (github.github.com/spec-kit, toolkit oficial de SDD do GitHub, compatível com Claude Code, Copilot e Gemini CLI). A Aula 4 já plantou essa ideia — hoje ela vira o ponto de partida oficial de todo prompt do curso.

Onde já vimos isso

Na Aula 4, a seção "Especificar o CRUD de protocolos" mostrou que os critérios de aceitação eram, quase palavra por palavra, os blocos [TAREFA] e [RESTRIÇÕES] do prompt. Hoje formalizaremos esse hábito com nome, estrutura e um fluxo mais complexo: a tramitação entre setores.

Exemplo

Pedir direto vs. pedir a partir de uma spec

Mesmo pedido — adicionar tramitação entre setores — dos dois jeitos.

Sem specadiciona um jeito de mudar o status do protocolo entre os setores

O que falta: quais status existem, quais transições são permitidas, quem pode fazer cada uma, o que fica registrado. A IA vai preencher cada lacuna com uma suposição própria — exatamente como na Aula 4.

Nascido de uma spec[PAPEL] Você é um desenvolvedor PHP sênior, especialista em sistemas administrativos para o setor público. [CONTEXTO] Projeto SISPROT. A tabela "protocolos" já existe, com status atual (Aberto, Em Análise, Deferido, Indeferido, Arquivado), mas sem histórico nem controle de quem pode mudar cada status. [TAREFA] Implemente a transição "Aberto → Em Análise". Critério de aceitação: toda mudança de status fica registrada num histórico (status anterior, novo status, data, setor responsável) e visível na tela do protocolo, do mais recente para o mais antigo. [RESTRIÇÕES] Não permita pular direto para "Deferido" ou "Indeferido" sem passar por "Em Análise". Sempre usar prepared statements. Não usar frameworks. [FORMATO] SQL da nova tabela de histórico primeiro; depois cada arquivo alterado, com o nome antes do código.

Reparem: o bloco [TAREFA] já é um critério de aceitação disfarçado — "fica visível no histórico, do mais recente para o mais antigo" é literalmente algo que dá para testar depois, item por item.

Etapa 2

Requisitos e casos de uso

O que o sistema faz, e como ele se comporta enquanto faz — duas perguntas diferentes.

Definição: requisito funcional vs. não funcional

Requisito funcional (RF) descreve o que o sistema faz — uma ação, uma regra de negócio. Requisito não funcional (RNF) descreve como o sistema se comporta enquanto faz isso — desempenho, segurança, auditabilidade (en.wikipedia.org/wiki/Functional_requirement). Os dois viram blocos diferentes dentro do prompt.

TipoExemplo aplicado à tramitaçãoVira, no prompt
RFO sistema deve permitir mudar o status de um protocolo, respeitando as transições permitidas.[TAREFA]
RNFToda mudança de status deve ficar registrada, com data e responsável.[TAREFA] / [FORMATO]
RNFSó usuários do setor responsável podem mudar o status de um protocolo.[RESTRIÇÕES]
Caso de uso

Um caso de uso descreve uma interação completa entre um ator e o sistema, com um objetivo (en.wikipedia.org/wiki/Use_case). "Servidor do setor Jurídico defere um protocolo em análise" é um caso de uso — vira a base da user story da próxima etapa.

Exercício rápido · individual · 10 min

RF e RNF do cartão de visita animado

10 min

Vamos retomar o cartão de visita animado da Aula 4 e aplicar o que acabamos de ver: separar requisito funcional de requisito não funcional, antes de escrever qualquer prompt.

Enunciado
  1. Escolheremos uma função nova para adicionar ao cartão: um botão "copiar e-mail" que dá uma confirmação visual ao ser clicado.
  2. Escreveremos 2 requisitos funcionais (RF) e 2 requisitos não funcionais (RNF) para essa função — sem pensar em código ainda.
  3. Traduziremos cada RF/RNF para um bloco do prompt: RF vira [TAREFA]; RNF vira [RESTRIÇÕES] ou [FORMATO], conforme o caso.
  4. Rodaremos o prompt resultante numa IA gratuita e testaremos o botão no navegador.

Se você não fez o exercício da Aula 4: tudo bem — descreva o cartão em 1-2 frases (nome, cargo, uma animação) antes do passo 1, ou peça para a IA recriá-lo rapidamente a partir dessa descrição.

Critério de sucesso
  • ✓Cada RF descreve uma ação; cada RNF descreve uma qualidade (desempenho, aparência, robustez).
  • ✓Conseguimos apontar, no prompt final, qual bloco veio de qual requisito.
  • ✓O botão funciona no navegador exatamente como os critérios descreveram.
Etapa 3

User stories e critérios de aceitação

A Aula 4 usou o formato uma vez, de leve. Hoje entendemos por que ele funciona.

Definição: user story + critérios de aceitação

Uma user story descreve uma necessidade do ponto de vista de quem usa o sistema ("Como / quero / para que"), pequena e testável o bastante para caber num prompt. Os critérios de aceitação são a lista do que precisa ser verdade para a história estar pronta (atlassian.com/agile/project-management/user-stories). Boas user stories seguem o critério INVEST: independentes, negociáveis, valiosas, estimáveis, pequenas, testáveis.

Exemplo

User story: mudar o status de um protocolo

Como servidor do setor responsável,
quero mudar o status de um protocolo que está sob minha análise,
para que o andamento fique visível para quem consulta o protocolo depois.

Critérios de aceitação
  • ✓Só é possível mudar para um status que seja uma transição permitida a partir do status atual.
  • ✓Toda mudança de status grava, no histórico: status anterior, novo status, data e setor responsável.
  • ✓O histórico aparece na tela do protocolo, do mais recente para o mais antigo.
  • ✓Um protocolo "Arquivado" não aceita mais nenhuma mudança de status.
Parte da user storyTextoVira, no prompt
Comoservidor do setor responsável[CONTEXTO] / [RESTRIÇÕES]
Queromudar o status de um protocolo que está sob minha análise[TAREFA]
Para queo andamento fique visível para quem consulta o protocolo depois[TAREFA] / [FORMATO]
Critério 1Só é possível mudar para um status que seja uma transição permitida a partir do status atual.[RESTRIÇÕES]
Critério 2Toda mudança de status grava, no histórico: status anterior, novo status, data e setor responsável.[TAREFA]
Critério 3O histórico aparece na tela do protocolo, do mais recente para o mais antigo.[FORMATO]
Critério 4Um protocolo "Arquivado" não aceita mais nenhuma mudança de status.[RESTRIÇÕES]
Por que isso importa

Repare: os critérios acima já são o roteiro de teste manual depois que a IA gerar o código. Especificar bem não é trabalho a mais — é o trabalho de decidir o que "pronto" significa, feito uma vez só, antes do prompt.

Exercício rápido · individual · 10 min

User story do cartão de visita animado

10 min

Mesma função do exercício anterior (o botão "copiar e-mail") — agora contada do ponto de vista de quem usa o cartão, não do sistema.

Enunciado
  1. Escreveremos a user story ("Como / quero / para que") para o botão "copiar e-mail", usando o exemplo desta etapa como modelo de estrutura.
  2. Listaremos de 3 a 4 critérios de aceitação — cada um precisa ser algo que dê para testar clicando no botão.
  3. Compararemos com os RF/RNF do exercício da Etapa 2: os critérios de aceitação deveriam cobrir os mesmos requisitos, só que na perspectiva de quem usa.
Critério de sucesso
  • ✓A user story segue o formato Como/quero/para que, sem menção a código.
  • ✓Cada critério de aceitação é testável manualmente (dá pra marcar "sim" ou "não" olhando o botão).
  • ✓Nenhum critério é vago ("deve funcionar bem") — todos descrevem um comportamento específico.
Etapa 4

Modelagem de fluxos e estados

A tramitação de protocolos, do início ao fim: os cinco status e quem pode mover cada um.

Definição: Step-Back Prompting

Técnica de pedir (ou fazer você mesmo) o princípio geral antes de aplicar a um caso específico — abstrair primeiro, especificar depois (arxiv.org/abs/2310.06117, "Take a Step Back: Evoking Reasoning via Abstraction in LLMs"). É exatamente o que faremos agora: em vez de especificar uma transição isolada (Aberto → Em Análise, depois Em Análise → Deferido, uma de cada vez), damos um passo atrás e modelamos o fluxo inteiro primeiro — a máquina de estados abaixo é o princípio geral; a spec de uma transição específica, logo depois, é o caso concreto aplicado a ele.

Definição: máquina de estados

Modelo que descreve os estados possíveis de algo (aqui, um protocolo) e as transições permitidas entre eles — deixando explícito o que não é permitido, não só o que é. Na Aula 4, só existia uma transição (Aberto → Arquivado). Hoje o fluxo completo entra em cena.

Fluxo completo de tramitação — cada seta é uma transição permitida; o resto é proibido por padrão.

Exemplo

Spec de uma transição específica

Em Análise → Deferido, restrita ao setor Jurídico.

Como servidor do setor Jurídico,
quero deferir um protocolo que está em análise,
para que o requerente saiba que o pedido foi aprovado.

  • ✓Só um protocolo com status "Em Análise" pode ser deferido.
  • ✓Só o setor "Jurídico" tem a opção de deferir disponível na tela.
  • ✓Deferir grava o histórico e muda o status para "Deferido".
Parte da user storyTextoVira, no prompt
Comoservidor do setor Jurídico[RESTRIÇÕES]
Querodeferir um protocolo que está em análise[TAREFA]
Para queo requerente saiba que o pedido foi aprovado[CONTEXTO]
Critério 1Só um protocolo com status "Em Análise" pode ser deferido.[RESTRIÇÕES]
Critério 2Só o setor "Jurídico" tem a opção de deferir disponível na tela.[RESTRIÇÕES] / [FORMATO]
Critério 3Deferir grava o histórico e muda o status para "Deferido".[TAREFA]
Exercício rápido · individual · 10 min

Estados de interação do cartão de visita animado

10 min

Um cartão animado também tem "estados" — não de um registro no banco, mas de interação na tela. Vamos aplicar o mesmo passo atrás (step-back) que usamos na tramitação.

Enunciado
  1. Modelaremos, em texto ou desenho simples, os estados de interação do cartão: por exemplo, Oculto → Visível (animação de entrada) → Hover → Clicado (copia e-mail ou abre link).
  2. Marcaremos quais transições são permitidas e quais não fazem sentido (ex.: não dá pra "clicar" num cartão ainda Oculto).
  3. Escolheremos uma transição específica (ex.: Hover → Clicado) e escreveremos a spec dela — user story + critérios de aceitação — como fizemos na Etapa 3.
Critério de sucesso
  • ✓O diagrama (ou lista) de estados cobre pelo menos 3 estados e deixa claro o que não é permitido.
  • ✓A spec da transição escolhida segue o mesmo formato usado na Etapa 3.
  • ✓Conseguimos explicar por que modelamos o fluxo inteiro antes de especificar só uma transição.

Preparar o mock para a tramitação

Exercício 1 · individual · 25 min

Da spec ao prompt: Aberto → Em Análise

25 min

Praticar o ciclo completo: escrever a spec primeiro, só depois o prompt — e verificar o código contra os critérios, um por um.

Enunciado
  1. Escreveremos a user story + critérios de aceitação para a transição "Aberto → Em Análise" (podemos adaptar o exemplo da Etapa 3).
  2. A partir da spec, escreveremos o prompt estruturado — cada critério deve aparecer, em algum bloco do prompt.
  3. Rodaremos o prompt na IA disponível e aplicaremos o resultado em protocolos-mock.html.
  4. Testaremos cada critério de aceitação manualmente, um por um, como um checklist.

Arquivo utilizado: protocolos-mock.html (gerado no "Ponto de partida" acima).

Dificuldades comuns

  • Escrever a spec depois do prompt, "para justificar" — a ordem importa: spec primeiro.
  • Critério vago demais ("deve funcionar bem") em vez de algo testável ("aparece no histórico, na ordem certa").
  • Esquecer de transformar a restrição de transição ("só a partir de Aberto") em bloco [RESTRIÇÕES] do prompt.

Dicas

  • Reaproveitaremos a user story da Etapa 3 como modelo de estrutura.
  • Cada critério de aceitação deveria virar uma linha do checklist de teste manual — se não conseguir, ele está vago demais.
Exercício 2 · individual · 30 min

Template reutilizável para novas transições

30 min

Criar um template — spec + prompt — reutilizável para qualquer transição nova, e aplicá-lo a "Em Análise → Deferido" e "Em Análise → Indeferido".

Enunciado
  1. Criaremos um template de prompt com placeholders como {{STATUS_ORIGEM}}, {{STATUS_DESTINO}} e {{SETOR_RESPONSAVEL}} — o mesmo padrão de "chamada" da Aula 4 (template colado + valores no final).
  2. Preencheremos o template duas vezes: uma para Em Análise → Deferido (setor Jurídico), outra para Em Análise → Indeferido (setor Jurídico).
  3. Para cada uma, rodaremos a chamada na IA e aplicaremos o resultado ao mesmo protocolos-mock.html.
  4. Testaremos as duas transições e confirmaremos que o setor Recepção não consegue mais deferir/indeferir diretamente.

Arquivo utilizado: protocolos-mock.html (estado atual do exercício).

Dificuldades comuns

  • Template de spec genérico demais: não distingue "quem" pode fazer a transição.
  • Esquecer de repetir a restrição "não pular estados" em cada preenchimento — ela é fixa, não parte do que varia.

Dicas

  • É a mesma "chamada" ensinada na Aula 4: colar o template inteiro de novo a cada transição, só trocando os valores no final.
  • Testaremos o template mentalmente com uma terceira transição hipotética antes de considerar pronto.
Desafio final · sem roteiro

Uma nova regra de permissão, do zero

15 min

Consolidar o ciclo completo — spec antes de prompt — com uma regra que a aula não cobriu.

Adicione ao nosso protocolos-mock.html uma nova regra: só o setor que abriu o protocolo pode arquivá-lo diretamente a partir de "Deferido" ou "Indeferido" — qualquer outro setor só pode visualizar.

Regras
  1. Escreveremos, nós mesmos, a spec (user story + critérios) do zero — sem copiar os exemplos da aula.
  2. Só depois escreveremos o prompt, a partir da nossa própria spec.
  3. Decidiremos os detalhes: o que a tela mostra para quem não tem permissão? Uma mensagem, ou o botão some?
  4. Testaremos manualmente, item por item, contra os critérios que escrevemos.
Critério de sucesso
  • ✓A spec (user story + critérios) foi escrita antes do prompt, não depois.
  • ✓O código gerado passa em todos os critérios, testados manualmente.
  • ✓Conseguimos explicar, em 1-2 frases, qual critério cada bloco do prompt resolve.

Spec 2 → Prompt 2

Transições controladas, com validação

Como responsável por manter a integridade do fluxo,
quero que só as transições previstas sejam aceitas,
para que nenhum protocolo pule etapas do processo.

Prompt 2 · validação de transição[PAPEL] Você é um desenvolvedor PHP sênior, especialista em sistemas administrativos para o setor público. [CONTEXTO] O SISPROT agora tem protocolo_historico e a coluna setor_atual (Prompt 1). As transições válidas são: Aberto → Em Análise; Em Análise → Deferido; Em Análise → Indeferido; Deferido → Arquivado; Indeferido → Arquivado. [TAREFA] Crie tramitar.php: recebe id do protocolo e novo status, valida se a transição é permitida a partir do status atual, grava o histórico e atualiza o status. Se a transição não for permitida, não altera nada e mostra uma mensagem de erro. [RESTRIÇÕES] Não permita nenhuma transição fora da lista acima. Sempre usar prepared statements. Não usar frameworks. [FORMATO] Só o arquivo tramitar.php, comentado indicando onde fica a validação das transições.
Spec 3 → Prompt 3

Tela de tramitação, com histórico visível

quero ver as próximas transições possíveis e o histórico completo na tela do protocolo,
para que eu não precise adivinhar o que posso fazer.

Prompt 3 · tela de tramitação[PAPEL] Você é um desenvolvedor PHP sênior, especialista em sistemas administrativos para o setor público. [TAREFA] Na listagem (listar.php), mostre o setor_atual como coluna, e adicione botões com as próximas transições válidas para aquele status ao lado dos botões já existentes (Editar/Excluir), apontando para tramitar.php. Reparem no padrão: cada prompt veio de uma spec (user story + critério), não do nada — é o ciclo fechado que hoje formalizamos.

Chat vs. agente de código

Com uma IA de chat, colamos o prompt inteiro numa mensagem e copiamos o código de volta. O Claude Code é diferente: ele já enxerga os arquivos da pasta e edita diretamente no disco — normalmente pedindo confirmação antes de alterar um arquivo ou rodar um comando.

Hoje, a especificação nasceu de nós, revisada à mão, antes de cada prompt. Na Aula 2, comparamos ferramentas — Claude Code, Copilot, Cursor e outras — construindo a mesma API a partir das mesmas specs, para entender onde cada uma se destaca.
