Etapa 1

Otimização de código com medição real

"Ficou mais rápido" não é dado — é impressão. Hoje a régua é o cronômetro.

Definição: otimização baseada em medição

Mudar código para ficar mais rápido, mas só decidir que funcionou depois de medir antes e depois, com o mesmo método, nas mesmas condições. Sem essa medição, uma mudança "otimizada" pode não ter feito diferença nenhuma — ou pode até ter piorado algo que ninguém percebeu a olho nu. Pedir para a IA "deixar mais rápido" sem pedir também a medição é repetir, na performance, o mesmo erro que o curso já cobriu para código gerado sem revisão: aceitar o resultado pela aparência, não pela evidência.

Cenário desta etapa

Um relatório novo no EmprestaTI — e um problema clássico de performance

A partir de hoje, o projeto de exemplo muda: em vez do SISPROT, vamos usar o EmprestaTI, um sisteminha fictício de empréstimo de equipamentos (notebooks, projetores) entre servidores — mesma estrutura simples de sempre (PHP + MySQL/PDO), domínio novo. Ele ganhou um relatório simples: quantos empréstimos cada equipamento já teve. A primeira versão, gerada rápido, funciona — mas tem um problema que só aparece quando o banco cresce.

// relatorio.php — versão inicial (aula-9/codigo/relatorio.php) $stmt = $pdo->query('SELECT id, nome FROM equipamentos ORDER BY nome'); $equipamentos = $stmt->fetchAll(); $contagem = []; foreach ($equipamentos as $equipamento) { $stmt = $pdo->prepare('SELECT COUNT(*) FROM emprestimos WHERE equipamento_id = ?'); $stmt->execute([$equipamento['id']]); $contagem[$equipamento['nome']] = $stmt->fetchColumn(); }

Definição: problema N+1

Um padrão clássico de lentidão: 1 consulta para buscar uma lista, e mais N consultas — uma para cada item da lista — para completar o resto da informação. No relatório acima: 1 consulta para listar os equipamentos, mais 1 consulta por equipamento para contar os empréstimos dele. Com 30 equipamentos, isso é 31 idas ao banco para responder uma pergunta que uma única consulta bem escrita resolveria.

Prompt · pedir medição antes de pedir otimização[PAPEL] Você é um desenvolvedor PHP com experiência em performance de banco de dados. [CONTEXTO] O arquivo relatorio.php do EmprestaTI (anexo) lista empréstimos por equipamento. Suspeito que ele faça uma consulta ao banco por equipamento, dentro de um loop. [TAREFA] Antes de propor qualquer otimização, adicione uma contagem de quantas consultas o código faz e quanto tempo total leva. Não mude a lógica ainda — só instrumente a medição. [FORMATO] O código com a instrumentação adicionada, e uma explicação de onde cada contagem é somada.

Pedir a medição antes da otimização, como um passo separado, é o que garante ter um "antes" para comparar — se pedirmos direto "otimize", perdemos a chance de provar que a mudança valeu a pena.

// Números medidos localmente (PHP + SQLite, 2.000 empréstimos fictícios, 30 equipamentos) — antes de publicar este material --- Versão com N+1 --- Consultas ao banco: 31 Tempo: 2,633 ms --- Versão otimizada (LEFT JOIN + GROUP BY) --- Consultas ao banco: 1 Tempo: 0,922 ms --- Comparação --- Redução de consultas: 31 → 1 (31x menos) Resultado: 2,9x mais rápido Resultados idênticos: SIM

Medido de verdade, com um script isolado, não estimado — script e método descritos em aula-9/codigo/README.md. Os números absolutos mudam de banco para banco e de máquina para máquina; o que não muda é a proporção do problema — trocar 31 idas ao banco por 1 é sempre uma redução grande, e numa rede real (não numa consulta local em memória, como neste teste) cada uma dessas 31 idas ainda carregaria a latência de rede até o servidor MySQL — a diferença tende a ser ainda maior em produção.

A versão corrigida

Uma consulta, com LEFT JOIN + GROUP BY, faz o mesmo trabalho

// relatorio.php — versão otimizada $stmt = $pdo->query( 'SELECT equipamentos.nome, COUNT(emprestimos.id) as total FROM equipamentos LEFT JOIN emprestimos ON emprestimos.equipamento_id = equipamentos.id GROUP BY equipamentos.id, equipamentos.nome ORDER BY equipamentos.nome' ); $contagem = []; foreach ($stmt as $linha) { $contagem[$linha['nome']] = $linha['total']; }

O banco de dados já sabe agrupar e contar — pedir isso numa única consulta SQL (GROUP BY) é sempre mais rápido que pedir ao PHP para fazer, uma pergunta de cada vez, o que o próprio banco faz de uma vez só. O LEFT JOIN (em vez de JOIN) garante que um equipamento sem nenhum empréstimo ainda apareça no relatório, com total zero.

Por que medir depois importa tanto quanto medir antes

Uma otimização só vale se o resultado continuar certo — não só rápido. Antes de aceitar a versão nova, comparamos as duas saídas campo a campo (no teste desta aula, "Resultados idênticos: SIM") — sem essa checagem, uma versão mais rápida mas errada seria pior que a lenta e certa. É o mesmo princípio de testes da Aula 3, agora aplicado a uma mudança de performance.

Exercício rápido · individual · 5 min

Isso tem N+1?

Para cada descrição abaixo, decida se o padrão tem um problema N+1, precisando de otimização (N), ou se já é uma única consulta bem escrita (O). A sequência correta das 6 respostas é a senha que libera o gabarito.

N = tem N+1, precisa otimizar  ·  O = uma consulta só, já está ok
  1. Buscar todos os empréstimos com uma consulta, depois um SELECT COUNT separado para cada equipamento da lista.
  2. Buscar equipamento e total de empréstimos numa única consulta com GROUP BY.
  3. Para cada um dos 50 empréstimos da tela, fazer uma consulta separada perguntando o nome do servidor responsável.
  4. Uma única consulta que já traz tudo que a tela precisa mostrar, incluindo nome do servidor via JOIN.
  5. Uma única consulta que já traz tudo que a tela precisa mostrar.
  6. Listar todos os equipamentos, depois abrir um SELECT COUNT(*) por equipamento dentro de um foreach.

1, 3 e 6 descrevem o mesmo padrão (uma consulta a mais por item de uma lista, dentro de um loop) — é N+1, não importa se é contar, buscar nome de setor, ou qualquer outra coisa. 2, 4 e 5 já resolvem tudo numa consulta só, com GROUP BY ou JOIN — nada a otimizar.

Etapa 2

Múltiplos agentes de IA na mesma tarefa

Uma conversa, um agente, um contexto — até a tarefa ficar grande demais para caber numa só.

Definição: subagente

Um assistente de IA especializado, com seu próprio contexto, que a conversa principal invoca para uma tarefa específica — e que devolve só o resultado, não todo o processo. A ideia central: uma tarefa que exigiria vasculhar 40 arquivos de log encheria a conversa principal de conteúdo que não importa depois; um subagente faz essa busca isolado, e volta só com a resposta. O Claude Code documenta oficialmente essa capacidade — cada subagente roda com prompt de sistema próprio, ferramentas específicas e permissões independentes (code.claude.com/docs/en/sub-agents).

Isso já aconteceu nesta aula

Boa parte da pesquisa por trás deste material — conferir a sintaxe exata de um comando, checar se uma página ainda está no ar, comparar várias fontes sobre o mesmo assunto — foi feita chamando um agente de pesquisa separado, que devolveu só a resposta resumida, sem encher a conversa principal com cada página visitada. É a mesma lógica que esta etapa está descrevendo, só que já em uso, não em teoria.

A turma usa Claude e GitHub Copilot — os quatro exemplos abaixo mostram os dois

Nada aqui é exclusivo do Claude Code. O GitHub Copilot, no VS Code, também tem agente próprio, subagentes de verdade e um agente autônomo em nuvem — com nomes e arquivos diferentes, mas resolvendo o mesmo problema. Os quatro blocos a seguir respondem, na ordem, às perguntas que mais aparecem quando alguém começa a usar agentes de IA de verdade.

// trecho de exemplo — padrão comum em formulários HTML com campo oculto, de qualquer sistema <?php if ($id): ?> <input type="hidden" name="id" value="<?= $id ?>"> <?php endif; ?>

$id, aqui, vem direto de $_GET ou $_POST, sem passar por htmlspecialchars() — um padrão de XSS real e comum, não exclusivo de nenhum sistema específico. É o trecho que os quatro exemplos abaixo usam — basta colar esse código na conversa, sem precisar de nenhum arquivo ou projeto instalado.

1 · Como criar um agente?

Um arquivo de texto com instruções — não é mais complicado que isso

Um agente especializado é, na prática, um arquivo Markdown com um cabeçalho (nome, descrição, quais ferramentas ele pode usar) e um prompt de sistema embaixo. Exemplo: um agente que revisa qualquer trecho de código PHP mostrado a ele — como o de cima — procurando saída HTML sem htmlspecialchars().

CampoPara que serve
nameIdentificador do agente — o nome do arquivo e o nome que aparece se você quiser chamá-lo diretamente (ex.: "use o agente revisor-seguranca").
descriptionO que decide quando o agente é acionado automaticamente: a ferramenta compara o pedido feito na conversa com essa descrição, e casa sozinha quando fazem sentido juntos — quanto mais específica, melhor o casamento.
toolsQuais ferramentas o agente pode usar. Aqui, só leitura (Read, Grep) — nunca escrita, porque a tarefa dele é revisar e apontar, não corrigir sozinho o código.
Texto depois do segundo ---O prompt de sistema — as instruções que definem como o agente deve se comportar, escritas como se estivesse falando diretamente com ele.

As duas linhas --- delimitam o cabeçalho YAML — tudo entre elas é configuração; tudo depois da segunda é o prompt de sistema, em texto livre.

Aprofundando: o campo tools, no Claude Code

No cabeçalho de um subagente do Claude Code, tools é uma allowlist — as ferramentas listadas, separadas por vírgula, são as únicas que aquele subagente pode usar (o exemplo revisor-seguranca acima usa tools: Read, Grep, por isso ele só lê e busca, nunca edita). Se o campo for omitido, o subagente herda todas as ferramentas disponíveis na sessão — a allowlist só existe para restringir, nunca é obrigatória.

FerramentaPara que serve
ReadLer arquivos
GrepBuscar texto/padrões
GlobBuscar arquivos por padrão de nome

Ferramentas de MCP também entram na lista: mcp__<servidor> libera todas as ferramentas daquele servidor MCP; mcp__<servidor>__<ferramenta> libera só uma específica.

Algumas ferramentas nunca ficam disponíveis a um subagente, mesmo se listadas em tools: AskUserQuestion, EnterPlanMode, ExitPlanMode (a menos que o subagente rode com permissionMode: plan), EndConversation, ScheduleWakeup, TaskOutput, WaitForMcpServers, Workflow, e Agent quando já no limite de profundidade de aninhamento (um subagente chamando outro que chamaria outro, indefinidamente). Faz sentido: são ferramentas que dependem de interação direta com quem está na conversa principal, ou que só fazem sentido uma vez por sessão.

# Claude Code — .claude/agents/revisor-seguranca.md --- name: revisor-seguranca description: Revisa trechos de código PHP em busca de saída HTML sem escape tools: Read, Grep --- Você revisa trechos de código PHP colados na conversa, procurando variáveis impressas em HTML sem passar por htmlspecialchars(). Para cada achado, aponte a linha e sugira a correção. # GitHub Copilot (VS Code) — .github/agents/revisor-seguranca.agent.md --- name: Revisor de Segurança description: Revisa trechos de código PHP em busca de saída HTML sem escape tools: ['search/codebase', 'read'] --- Você revisa trechos de código PHP colados na conversa, procurando variáveis impressas em HTML sem passar por htmlspecialchars(). Para cada achado, aponte a linha e sugira a correção.

Mesma ideia, dois formatos quase idênticos: cabeçalho YAML + instruções em texto simples. O caminho muda (.claude/agents/ vs. .github/agents/), a lógica não. Em ambos, também dá para simplesmente pedir — "crie um agente que revise saídas HTML sem escape" — e deixar a própria ferramenta escrever o arquivo.

Passo a passo, depois de salvar o arquivo
  1. Salvar o arquivo no caminho exato acima — dentro do projeto, não solto em outra pasta.
  2. Pedir uma tarefa que bata com a description do agente — não precisa chamar o agente pelo nome, a ferramenta casa sozinha (ex.: "revise este trecho: [colar o código acima] procurando saída sem escape").
  3. Confirmar que o agente certo respondeu, perguntando de volta: "qual agente você usou para isso?".
2 · Como ver o agente funcionando?

"Funcionou" não é suficiente — é preciso conseguir ver o que ele fez

O mesmo princípio de transparência do curso inteiro, aplicado a um agente: nunca confiar só porque ele disse que terminou.

# Claude Code — achado real, rodando o agente do bloco 1 sobre o trecho colado (testado de verdade, não ilustrativo) ⏺ Task(revisor-seguranca): revisar o trecho de código colado na conversa ⎿ Achado: XSS refletido em atributo HTML — linha 2, sem escape ⎿ Cenário de exploração: $id = '"><script>alert(document.cookie)</script>' fecha a tag value="..." e injeta um <script> executado ao carregar ⎿ Correção: value="<?= htmlspecialchars($id, ENT_QUOTES, 'UTF-8') ?>" ⎿ Concluído — 1 achado # GitHub Copilot (Chat, agent mode) — mesmo padrão, formato ilustrativo (não testado neste material) ▸ Analyzed pasted snippet ▸ Ran search: htmlspecialchars ▸ Found 1 issue — XSS via unescaped $id, line 2 ▸ Summary: 1 achado, com cenário de exploração e correção sugerida

O achado do Claude Code acima não é um exemplo fabricado para o material — é a saída real do agente revisor-seguranca rodando sobre o trecho desta etapa. Repare que ele não só apontou a falta de htmlspecialchars(): também explicou o cenário de exploração (o payload que quebra o atributo) e recomendou ENT_QUOTES, 'UTF-8' — mais preciso que só "use htmlspecialchars()", porque sem ENT_QUOTES o escape de aspas depende da versão e configuração do PHP. Antes de aceitar qualquer resultado de agente, três coisas precisam aparecer: qual agente rodou, o que ele analisou, e o que ele concluiu — se uma faltar, peça para detalhar antes de confiar.

3 · Como delegar para um subagente?

Pedir, nomeando a tarefa e o que deve voltar

Claude Code · delegação implícita, pelo tipo de tarefaEnquanto revisamos este trecho juntos, use um agente separado para pesquisar: quais outras funções do PHP, além de htmlspecialchars(), também protegem contra saída insegura, e quando cada uma se aplica (atributo HTML, JavaScript, URL). Quero só uma lista curta com justificativa, não o processo de pesquisa.
GitHub Copilot · delegação explícita, com #runSubagent#runSubagent Rode o agente "Revisor de Segurança" para revisar este trecho: [colar o código do exemplo acima] procurando saída sem htmlspecialchars(). Quero só a lista de achados.

O ganho não é velocidade — muitas vezes é o oposto, já que rodar um subagente tem custo próprio. O ganho é a conversa principal continuar limpa, sem se perder em conteúdo que só importava para a pesquisa ou a revisão, não para o código sendo escrito agora.

4 · Como montar um time de agentes?

Mais de um especialista, cada um com seu escopo, ao mesmo tempo

Cenário: um agente revisando segurança (o trecho de saída HTML sem escape, do topo desta etapa) e outro otimizando um trecho com problema N+1 (o de baixo), rodando ao mesmo tempo — sem um atrapalhar o outro, porque cada um trabalha sobre um trecho de código diferente.

// trecho de exemplo 2 — problema N+1, para o segundo agente do time $stmt = $pdo->query('SELECT DISTINCT categoria FROM produtos'); $categorias = $stmt->fetchAll(PDO::FETCH_COLUMN); $contagem = []; foreach ($categorias as $categoria) { $stmt = $pdo->prepare('SELECT COUNT(*) FROM produtos WHERE categoria = ?'); $stmt->execute([$categoria]); $contagem[$categoria] = $stmt->fetchColumn(); }

Mesmo padrão da Etapa 1 (uma consulta para listar, mais uma consulta por item dentro do loop), só que genérico — não precisa de nenhum arquivo ou banco instalado, basta colar este trecho na conversa junto com o de segurança do topo.

# Claude Code — agent teams é experimental, precisa ser ligado antes # uma vez, no ~/.claude/settings.json: { "env": { "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1" } } # ou, só para essa sessão: CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 claude

Agent teams vem desligado por padrão, por ainda ser experimental — sem uma dessas duas linhas, pedir "use agent teams" não faz nada, o Claude Code ignora. A diferença entre as duas: a primeira (dentro do settings.json) liga o recurso para sempre, em toda sessão futura, até alguém tirar essa linha de novo; a segunda (o prefixo antes de claude) liga só para aquela sessão que está sendo aberta — da próxima vez que rodar claude sem o prefixo, volta desligado. Para só testar uma vez, a segunda opção evita mexer em configuração permanente.

Claude Code · pedindo o time, depois de ligar o recurso e referenciar o arquivoUse agent teams para trabalhar em paralelo no arquivo @exemplo.php. Um agente revisa o primeiro trecho (saída HTML sem escape), outro revisa o segundo (a consulta dentro do loop) e propõe a versão com GROUP BY. No final, sintetize os dois resultados num único resumo.

Uma sessão vira "team lead": divide o pedido em duas tarefas, cada agente trabalha no seu próprio contexto, e a sessão principal junta os dois resultados no final — sem um agente ver o histórico do outro enquanto trabalha. Não precisa nomear os agentes dos blocos 1-3 — basta descrever as duas tarefas, e o team lead casa cada uma com o especialista certo.

# GitHub Copilot — duas issues delegadas ao coding agent, viram time por serem paralelas gh issue edit 101 --add-assignee "@copilot" # issue: revisar o trecho 1 (saída sem escape) gh issue edit 102 --add-assignee "@copilot" # issue: otimizar o trecho 2 (consulta N+1)

Apenas um exemplo de uso — 101 e 102 são números ilustrativos, não issues que existem de verdade neste curso. Para rodar isso de fato, é preciso um repositório no GitHub com Copilot habilitado, e issues reais criadas nele (com o número de cada uma) descrevendo essas duas tarefas.

Cada issue vira, sozinha, uma sessão independente do coding agent — que trabalha num sandbox do GitHub Actions e devolve um Pull Request. Duas issues ao mesmo tempo já são, na prática, um time: mais próximo de dois PRs revisados depois do que de uma conversa única coordenando os dois. Para um time dentro da mesma conversa, o caminho mais maduro do Copilot hoje é rodar dois #runSubagent na mesma mensagem, um para cada tarefa.

Exercício prático · individual · 15 min

Crie seu próprio agente — com SQL, dessa vez

Os quatro exemplos desta etapa usaram sempre o mesmo tipo de problema (saída HTML sem escape, N+1). Agora é sua vez, com um terceiro problema: injeção de SQL por concatenação de string, em vez de parâmetro vinculado.

// trecho de exemplo — para o exercício, ainda não usado nesta etapa $sql = "SELECT * FROM produtos WHERE nome = '" . $_GET['nome'] . "'"; $resultado = $pdo->query($sql);

Diferente do exemplo de segurança do topo (saída sem escape) e do de N+1 do bloco 4 (consulta repetida em loop) — aqui o problema é outro: $_GET['nome'] entra direto na string do SQL, sem passar por prepare()/execute() com parâmetro.

# Claude Code — .claude/agents/revisor-sql.md --- name: revisor-sql description: Revisa trechos de código PHP com SQL montado por concatenação de string, sem parâmetro vinculado tools: Read, Grep --- Você revisa trechos de código PHP com consultas SQL, procurando strings SQL montadas por concatenação com dado de entrada não confiável ($_GET, $_POST, etc.), em vez de prepared statement com parâmetro vinculado. Para cada achado, aponte a linha, explique um cenário de exploração com um valor concreto que quebra a consulta, e proponha a correção com prepare()/execute() e parâmetro vinculado. # GitHub Copilot (VS Code) — .github/agents/revisor-sql.agent.md --- name: Revisor de SQL description: Revisa trechos de código PHP com SQL montado por concatenação de string, sem parâmetro vinculado tools: ['search/codebase', 'read'] --- Você revisa trechos de código PHP com consultas SQL, procurando strings SQL montadas por concatenação com dado de entrada não confiável ($_GET, $_POST, etc.), em vez de prepared statement com parâmetro vinculado. Para cada achado, aponte a linha, explique um cenário de exploração com um valor concreto que quebra a consulta, e proponha a correção com prepare()/execute() e parâmetro vinculado.

Mesmo formato do revisor-seguranca do bloco 1 — só a especialidade muda. Pode salvar exatamente assim e usar, ou pedir "crie um agente que detecte SQL montado por concatenação" e deixar a própria ferramenta escrever o arquivo.

O que o seu agente precisa entregar
  1. Criar um agente (no formato do bloco 1, .claude/agents/ ou .github/agents/) especializado em detectar consultas SQL montadas por concatenação de string, com dado de entrada não confiável.
  2. Colar o trecho acima na conversa e pedir para o agente revisar.
  3. Conferir se a resposta traz, no mínimo, as três coisas que o revisor-seguranca do bloco 2 trouxe para o exemplo de XSS: onde está o problema (com a linha), um cenário de exploração real (um valor de nome que quebra a consulta — ex.: fechando as aspas e adicionando uma condição sempre verdadeira), e a correção com prepare()/parâmetro vinculado.
Critério de sucesso
  • ✓O agente existe como arquivo, não como instrução repetida a cada pergunta.
  • ✓A resposta aponta a linha exata e explica, com um valor concreto de nome, como a consulta é quebrada.
  • ✓A correção sugerida usa parâmetro vinculado (? ou :nome), não apenas escapar aspas manualmente.

Etapa 3

O que é o Model Context Protocol (MCP)

Um jeito padrão de uma IA se conectar a dados e ferramentas de verdade — não mais um por ferramenta.

Definição: MCP (Model Context Protocol)

Um protocolo aberto, criado pela Anthropic, para conectar aplicações de IA a sistemas externos — fontes de dados (arquivos locais, bancos de dados), ferramentas (buscadores, calculadoras) e fluxos de trabalho (prompts especializados). A própria documentação oficial usa a analogia: MCP é como uma porta USB-C para aplicações de IA — assim como USB-C padronizou como conectar aparelhos eletrônicos, o MCP padroniza como conectar uma IA a qualquer sistema externo, sem precisar de uma integração feita à mão para cada ferramenta (modelcontextprotocol.io/introduction). É um protocolo aberto, com suporte de Claude, ChatGPT, VS Code, Cursor e outras ferramentas — não é exclusivo de nenhuma delas.

O host cria um cliente para cada servidor conectado; cada servidor expõe algum conjunto de tools, resources e prompts.

Definição: os três primitivos de um servidor MCP

Tools são ações executáveis — algo que a IA pode chamar para fazer alguma coisa (ex.: buscar um equipamento pelo número de patrimônio). Resources são dados que a IA pode consultar como contexto, mas não executar (ex.: o schema do banco do EmprestaTI). Prompts são modelos prontos de interação, reutilizáveis (ex.: um template para gerar um relatório mensal). Um mesmo servidor pode oferecer os três tipos ao mesmo tempo — a IA descobre o que está disponível ao se conectar, sem precisar saber de antemão (modelcontextprotocol.io/.../architecture).

MCP e RAG resolvem um problema parecido, de jeitos diferentes

A Aula 8 ensinou RAG: buscar um trecho de texto e colar no prompt antes de responder. MCP também dá à IA acesso a informação que ela não tem de cabeça — mas em vez de um texto estático colado no prompt, é uma conexão viva: a IA pode consultar, e em muitos casos até agir (uma tool pode alterar dado, não só ler). RAG resolve "a IA não sabe isso"; MCP resolve "a IA não consegue chegar nisso sozinha, nem fazer nada a respeito".

Etapa 4

MCP na prática: conectando uma IA a uma fonte real

Instalar um servidor MCP leva um comando. Confiar nele é a parte que exige critério.

Definição: instalar um servidor MCP no Claude Code

Comando geral, para um servidor local (stdio): claude mcp add <nome> -- <comando> <argumentos...>. Exemplo oficial: claude mcp add context7 -- npx -y @upstash/context7-mcp. Também existe a opção de escopo — --scope project (compartilhado via git com quem clonar o projeto) ou --scope user (disponível em todos os seus projetos, só para você). Depois de adicionado, o Claude Code se conecta ao servidor e busca sozinho a lista de tools, resources e prompts que ele oferece — não é preciso descrever isso manualmente (code.claude.com/docs/en/mcp).

Cenário desta etapa: consultar documentação real, não a memória do modelo, via MCP

Context7 é um servidor MCP que busca documentação atual de linguagens e bibliotecas direto da fonte, no momento da pergunta — em vez de confiar só no que o modelo aprendeu no treinamento (que pode estar desatualizado, ou nunca ter existido, se a versão for recente). Cenário: um time de PHP está avaliando trocar os parâmetros posicionais (?) do PDO::prepare() por parâmetros nomeados (:campo). Antes de mudar, confirmar a sintaxe e as restrições atuais direto da documentação oficial do PHP, não da lembrança do modelo.

Diferente do exemplo de banco de dados que este material já teve — aqui não se instala nada

Context7 roda via npx, o mesmo comando já usado no exercício de sistema de arquivos da "Mão na massa" — sem banco, sem servidor, sem conta obrigatória (uma chave de API é opcional, só para aumentar o limite de uso). Se o Node.js já está instalado (pré-requisito do curso desde as primeiras aulas), não falta mais nada.

# Já citado acima como o exemplo oficial de instalação — repetido aqui como o exemplo prático desta etapa claude mcp add context7 -- npx -y @upstash/context7-mcp # Conferir que conectou claude mcp list

Depois de rodar claude mcp add, o Claude Code costuma avisar que é preciso reiniciar a sessão para as ferramentas do servidor ficarem disponíveis — o cliente MCP só é montado quando o processo inicia, então adicionar um servidor no meio de uma sessão não é suficiente. O procedimento: (1) sair da sessão atual (/exit, ou Ctrl+D); (2) abrir de novo, na mesma pasta do projeto (claude); (3) confirmar com claude mcp list, ou perguntando direto "quais ferramentas você tem disponíveis agora?". Não precisa fechar o terminal nem reiniciar o VS Code — só encerrar e reabrir o processo do claude.

O mesmo servidor funciona no GitHub Copilot

O agent mode do Copilot, no VS Code, já suporta servidores MCP — hoje por transporte stdio. Como o Context7 roda localmente por stdio, o mesmo servidor conecta no Copilot, com um arquivo de configuração no workspace:

// .vscode/mcp.json { "servers": { "context7": { "type": "stdio", "command": "npx", "args": ["-y", "@upstash/context7-mcp"] } } }

Mesmo servidor, mesmo comando — só o formato do arquivo muda (JSON, não linha de comando).

Passo a passo, no VS Code
  1. Criar a pasta .vscode na raiz do workspace (se ainda não existir), e dentro dela o arquivo mcp.json com o conteúdo acima.
  2. Com o arquivo aberto no editor, aparece um link clicável Start em cima da entrada do servidor — clicar nele inicia o Context7. (Alternativa: Command Palette → MCP: List Servers → selecionar context7 → iniciar.)
  3. Confirmar que conectou: rodar de novo MCP: List Servers na Command Palette — o servidor aparece como ativo, com a lista de tools que ele expõe.
  4. Abrir o Chat (Ctrl+Alt+I) e trocar o modo, no menu suspenso da caixa de mensagem, de Ask para Agent — as tools de servidores MCP só ficam disponíveis nesse modo. O botão Configure Tools, na própria caixa de chat, mostra e permite ligar/desligar cada tool individualmente antes de perguntar.
Consultar, aplicar, confirmar

Três prompts — sempre com a fonte, nunca só a resposta

1 · Consultar a documentação atualUsando o Context7, busque a documentação do PHP sobre PDOStatement::execute() — especificamente: dá para misturar parâmetros nomeados (:campo) e posicionais (?) na mesma consulta preparada?
# Resposta esperada e correta — dá para conferir em php.net, independente do modelo Não. Uma mesma instrução preparada precisa escolher um estilo só — todo nomeado (:campo) ou todo posicional (?). Misturar os dois na mesma consulta não é suportado.
// trecho de exemplo — cole isso na conversa junto com o prompt 2, abaixo $stmt = $pdo->prepare('SELECT COUNT(*) FROM produtos WHERE categoria = ?'); $stmt->execute([$categoria]);
2 · Aplicar a um trecho de código realEsse trecho usa parâmetro posicional. Reescreva-o (prepare + execute) usando parâmetro nomeado.
// Resposta esperada e correta $stmt = $pdo->prepare('SELECT COUNT(*) FROM produtos WHERE categoria = :categoria'); $stmt->execute(['categoria' => $categoria]);

Mesmo padrão do trecho de N+1 já usado na Etapa 2 (Bloco 4) — genérico, sem precisar de nenhum arquivo ou sistema específico.

3 · Confirmar a única coisa que realmente importa aquiEssa troca muda alguma coisa na proteção contra SQL injection, comparado com o parâmetro posicional que já estava lá?

Resposta esperada e correta: não muda nada — os dois estilos usam parâmetro vinculado (prepared statement) da mesma forma, e protegem igual contra SQL injection. A escolha entre nomeado e posicional é só de legibilidade do código, nunca de segurança. É exatamente esse tipo de resposta que confirma o valor do Context7 aqui: sem ele, o modelo poderia responder de memória e errar numa mudança recente do PHP; com ele, a resposta vem de documentação atual, com fonte — a mesma diferença que a Aula 8 já ensinou entre confiar de cabeça e confiar com uma fonte citada.

Os três prompts acima e suas respostas são fatos verificáveis (documentação do PHP, sintaxe real do PDO) — não depende de MySQL, Postgres, nem de nenhum banco de dados rodando para ser testado de verdade em sala.

Exercício rápido · individual · 5 min

Verdadeiro ou falso?

Para cada afirmação abaixo sobre usar MCP no Claude Code, decida se é verdadeira (V) ou falsa (F). A sequência correta das 6 respostas é a senha que libera o gabarito.

V = verdadeiro  ·  F = falso
  1. claude mcp add nome -- comando args é a sintaxe geral para conectar um servidor MCP local (stdio).
  2. Um servidor instalado com --scope project fica disponível só para quem instalou, nunca para quem clonar o repositório.
  3. --scope user deixa o servidor disponível em todos os seus projetos, não só no atual.
  4. Depois de conectado, o Claude Code busca sozinho a lista de tools, resources e prompts do servidor.
  5. É preciso escrever manualmente, em JSON, a lista de tools de um servidor MCP antes de poder usá-lo.
  6. Servidores MCP só existem para sistema de arquivos — bancos de dados e APIs não têm suporte.

1, 3 e 4 são exatamente o que a documentação oficial descreve. 2 é o oposto do real: --scope project é compartilhado via git com quem clonar o projeto — é --scope user que fica só com quem instalou. 5 é falso — a descoberta de tools é automática, o cliente pergunta ao servidor. 6 é falso — bancos de dados e APIs têm servidores de referência oficiais, arquivos é só o exemplo mais simples.

Etapa 5

Riscos e limites

Medir errado, coordenar mal, ou conectar sem checar — os três temas de hoje têm sua própria forma de dar errado.

Definição: otimização prematura

"Devíamos esquecer pequenas eficiências, digamos em 97% do tempo: otimização prematura é a raiz de todo mal" — frase atribuída a Donald Knuth, num dos textos mais citados da engenharia de software. Aplicada a esta aula: otimizar algo que não é o gargalo real, sem medir primeiro onde o tempo está indo, é gastar esforço (e arriscar introduzir bug) por um ganho que talvez nem exista. A régua da Etapa 1 — medir antes, medir depois — é exatamente o antídoto para esse risco.

Medir no ambiente errado engana tanto quanto não medir

Uma otimização testada com 10 registros de banco pode não mostrar diferença nenhuma — e a mesma mudança, nos 50 mil registros reais da produção, pode ser a diferença entre 1 segundo e 1 minuto. O oposto também acontece: uma "otimização" que parece ótima com poucos dados pode se comportar mal em volume real. Medir com dado parecido com o real (em volume, não necessariamente sensível) é parte da disciplina, não um detalhe.

RiscoO que dá errado
Múltiplos agentes: conflito de ediçãoDois agentes mexendo no mesmo arquivo ao mesmo tempo podem sobrescrever o trabalho um do outro — quem coordena precisa dividir o trabalho por área, não só "mandar os dois tentarem".
Múltiplos agentes: custo multiplicadoCada agente consome tokens de forma independente — rodar três agentes numa tarefa que um resolveria sozinho triplica o custo sem necessariamente triplicar a qualidade.
MCP: Tool PoisoningUm servidor MCP malicioso pode devolver, junto com o dado pedido, uma instrução escondida na resposta — a IA trata tudo como contexto confiável e pode acabar executando uma ação que ninguém pediu (ex.: ler um arquivo sensível e enviá-lo para fora). É uma categoria de ataque reconhecida pela própria OWASP.

Sobre Tool Poisoning: mitigação recomendada inclui exigir respostas estruturadas (schema fixo), isolar ferramentas sensíveis, não confiar só em instrução de prompt para controle de acesso, usar apenas servidores de uma lista de confiança, e pedir confirmação explícita antes de ações sensíveis (owasp.org/www-community/attacks/MCP_Tool_Poisoning) — a mesma lógica de "verificar antes de instalar" já vista na Aula 6 para skills de terceiros, e na Aula 8 para envenenamento de índice de RAG.

Exercício rápido · individual · 5 min

Qual dos três riscos é esse?

Para cada cenário abaixo, identifique a qual dos três temas desta aula o risco pertence. A sequência correta das 6 respostas é a senha que libera o gabarito.

O = risco de otimização/medição  ·  A = risco de múltiplos agentes  ·  M = risco de MCP
  1. Um servidor MCP malicioso devolve, junto com o dado pedido, uma instrução escondida para ler um arquivo de senhas.
  2. Dois agentes editam o mesmo arquivo ao mesmo tempo, e um sobrescreve o trabalho do outro.
  3. Uma equipe reescreve uma função que já era rápida, sem medir antes — o sistema não fica perceptivelmente mais rápido, só mais arriscado.
  4. O custo em tokens triplica porque três agentes trabalham em paralelo numa tarefa simples que um resolveria sozinho.
  5. A medição de performance rodou só com 10 registros de teste, e a versão "otimizada" piora com os 50 mil registros reais.
  6. Um servidor MCP diz, na própria lista de tools, que pode "ler qualquer arquivo do sistema" — e ninguém checou essa permissão antes de conectar.

1 e 6 são risco de MCP (instrução escondida na resposta; permissão excessiva não checada). 2 e 4 são risco de múltiplos agentes (conflito de edição; custo multiplicado). 3 e 5 são risco de otimização/medição (mudar sem medir; medir no ambiente errado).

  • ✓Tentar cadastrar um empréstimo para um equipamento já emprestado (sem devolução) é recusado, com o nome de quem está com ele.
  • ✓Cadastrar um empréstimo para um equipamento livre continua funcionando normalmente.
  • ✓Nenhum outro arquivo do EmprestaTI foi alterado além de emprestimo_form.php.

Dificuldades comuns

  • Na tela de autorização, esquecer de marcar a página criada no Passo 1 (ou o workspace) no seletor — a conexão fica de pé, mas a busca não encontra nada.
  • A IA implementar mais do que a especificação pede (ex.: criar uma tela de histórico de conflitos) — o "fora de escopo" da especificação existe exatamente para evitar isso; vale cobrar se acontecer.

Dicas

  • Se sobrar tempo, edite a página no Notion (ex.: mude a mensagem de erro pedida) e peça para a IA implementar de novo — sem tocar em nada além da página, para sentir a mesma "conexão viva" que a Etapa 3 descreveu.
Exercício 4 · individual · 20 min · MCP #2

GitHub Issues — relatar e corrigir

20 min

Mesmo padrão do Exercício 3, com outra ferramenta: em vez de uma especificação no Notion, um bug relatado como issue do GitHub — o formato mais comum de "pedido de mudança" em qualquer projeto real. O bug é real, não fabricado: emprestimo_form.php valida que as duas datas existem e têm formato válido, mas nunca confere se a devolução prevista vem depois da retirada.

Passo 1 · a issue

Abra um repositório de teste no GitHub e crie esta issue

Issue · título e corpo, para colar num repositório de testeTítulo: Sistema aceita devolução prevista antes da data de retirada Corpo: Ao cadastrar um novo empréstimo em emprestimo_form.php, é possível escolher uma "Devolução prevista" anterior à "Data de retirada" — por exemplo, retirada em 20/03/2026 e devolução prevista em 15/03/2026 é aceito sem nenhum erro. Comportamento esperado: o cadastro deveria ser recusado, com uma mensagem clara, sempre que a devolução prevista vier antes (ou no mesmo dia, se quiser ser mais rígido) da data de retirada. Arquivo afetado: aula-9/codigo/emprestimo_form.php

Pode ser um repositório pessoal vazio, criado só para o exercício — o conteúdo da issue é fictício, mas a validação que falta é real, a mesma coisa que aconteceria numa auditoria de código de verdade.

Passo 2 · conectar o GitHub

Token e o servidor oficial (versão remota, sem Docker)

  1. Gerar um Personal Access Token em github.com/settings/personal-access-tokens/new — escopo de leitura de issues já basta para este exercício.
  2. O servidor MCP oficial do GitHub (github/github-mcp-server) tem uma versão remota, hospedada pela própria GitHub — não precisa instalar nada localmente, nem Docker.
# Claude Code — versão remota, sem Docker claude mcp add-json github '{"type":"http","url":"https://api.githubcopilot.com/mcp","headers":{"Authorization":"Bearer SEU_TOKEN_AQUI"}}' # Conferir que conectou claude mcp list

Existe também uma versão local via Docker, com login OAuth pelo navegador em vez de token colado à mão — mais segura para uso contínuo, mas exige Docker instalado; para o exercício de hoje, a versão remota com token é suficiente.

# GitHub Copilot (VS Code) — .vscode/mcp.json { "servers": { "github": { "type": "http", "url": "https://api.githubcopilot.com/mcp", "headers": { "Authorization": "Bearer SEU_TOKEN_AQUI" } } } }
Passo 3 · pedir a correção

O prompt final

Prompt · buscar a issue no GitHub e corrigirBusque, no meu repositório, a issue sobre devolução prevista antes da retirada. Corrija exatamente o que ela descreve em aula-9/codigo/emprestimo_form.php — validando que a devolução prevista vem depois da data de retirada, com uma mensagem de erro clara caso não venha.

Diferente do Notion, aqui a IA está lendo um formato bem mais estruturado (título, corpo, rótulos) — bom contraste para notar que "especificação" pode vir em formatos bem diferentes, e o MCP se adapta a cada um sem mudar o jeito de pedir.

  • ✓Tentar salvar um empréstimo com devolução prevista antes da retirada é recusado, com mensagem clara.
  • ✓Datas em ordem normal continuam sendo aceitas, sem regressão.
  • ✓A IA citou a issue (número/título) ao explicar o que fez — sinal de que a busca via MCP funcionou.

Dificuldades comuns

  • Token sem permissão de leitura de issues, ou colado com espaço/quebra de linha a mais — a mensagem de erro do claude mcp list geralmente aponta isso.

Dicas

  • Se sobrar tempo, peça para a IA comentar na própria issue, resumindo a correção feita — fechando o ciclo "relatado → corrigido → documentado" que qualquer projeto real usa.
Exercício 5 · individual · 20 min · MCP #3

Google Sheets — importar em lote

20 min

O terceiro exemplo, com dado estruturado em vez de texto: uma planilha do Google Sheets com uma lista de equipamentos novos, que a IA vai ler via MCP e transformar em cadastro. É, de propósito, a conexão mais trabalhosa de configurar das três — um bom lembrete de que "conectar via MCP" nem sempre é um comando só, e vale levar isso em conta na hora de escolher uma ferramenta.

Passo 1 · a planilha

Crie uma planilha nova no Google Sheets com estas colunas

nomepatrimoniotipo
Notebook Dell 5420PAT-2031Notebook
Projetor Epson X400PAT-2032Projetor
Webcam Logitech C920PAT-2033Webcam

Três linhas já bastam para o exercício — o objetivo é ver a importação em lote acontecendo, não testar volume.

Passo 2 · conectar o Google Sheets

Service account — mais etapas que Notion ou GitHub

  1. No Google Cloud Console, criar (ou reaproveitar) um projeto, e ativar a "Google Sheets API" em "APIs & Services" → "Library".
  2. Em "APIs & Services" → "Credentials" → "Create Credentials" → "Service Account", criar uma conta de serviço; depois, nos três pontos dela → "Manage keys" → "Add key" → "Create new key" → JSON, baixando o arquivo.
  3. Abrir o JSON baixado e copiar o campo client_email — na planilha do Passo 1, clicar em "Share" e adicionar esse e-mail como Editor.
# Claude Code — servidor comunitário mcp-gsheets, mantido ativamente claude mcp add sheets --env GOOGLE_PROJECT_ID=seu-projeto-id --env GOOGLE_APPLICATION_CREDENTIALS=/caminho/absoluto/para/service-account-key.json -- npx -y mcp-gsheets@latest # Conferir que conectou claude mcp list

Diferente do Notion e do GitHub, o Google Sheets não tem um servidor MCP oficial da própria Google com o mesmo nível de simplicidade — o mcp-gsheets é comunitário, mas ativamente mantido; é a mesma checagem de confiança da Etapa 5 (quem mantém, quantas issues em aberto, quando foi a última atualização) antes de instalar qualquer servidor de terceiros.

# GitHub Copilot (VS Code) — .vscode/mcp.json { "servers": { "sheets": { "type": "stdio", "command": "npx", "args": ["-y", "mcp-gsheets@latest"], "env": { "GOOGLE_PROJECT_ID": "seu-projeto-id", "GOOGLE_APPLICATION_CREDENTIALS": "/caminho/absoluto/para/service-account-key.json" } } } }
Passo 3 · pedir a importação

O prompt final

Prompt · ler a planilha e gerar o cadastroLeia a planilha [nome/URL da sua planilha] via Google Sheets e gere os comandos SQL de INSERT para cadastrar cada linha na tabela equipamentos do EmprestaTI (colunas: nome, patrimonio, tipo). Não execute nada — só mostre os comandos gerados, para eu conferir antes de rodar.

Pedir para gerar o SQL em vez de já rodar direto no banco é de propósito — é a mesma cautela da Etapa 5 desta aula com tools que alteram dado: revisar antes de deixar a IA agir, principalmente numa conexão nova, ainda não testada.

  • ✓A IA leu as três linhas certas da planilha, sem inventar nem pular nenhuma.
  • ✓Os comandos SQL gerados batem com os dados exatos da planilha (nome, patrimônio, tipo).
  • ✓Nada foi executado no banco sem revisão — só o SQL foi gerado, como pedido.

Dificuldades comuns

  • Esquecer de compartilhar a planilha com o e-mail da service account — o erro mais comum aqui, equivalente a esquecer de marcar a página certa na autorização do Notion.
  • GOOGLE_APPLICATION_CREDENTIALS com caminho relativo em vez de absoluto — use sempre o caminho completo do arquivo JSON baixado.

Dicas

  • Se este exercício ficar de fora por falta de tempo, os Exercícios 3 e 4 já cobrem os dois lados mais comuns de MCP (texto livre e formato estruturado tipo issue) — Sheets é o "terceiro degrau", não o essencial.
Desafio final · sem roteiro

Otimizar e documentar com evidência

25 min

Juntar performance, medição e documentação — o EmprestaTI ganha um registro formal de uma otimização real.

Escolheremos uma parte do EmprestaTI (pode ser o próprio index.php, o relatorio.php com outra métrica, ou algo criado por conta própria) e aplicaremos o ciclo completo: medir, otimizar, medir de novo, documentar a diferença com números reais — não com "ficou mais rápido".

Regras
  1. A medição "antes" precisa existir antes de qualquer mudança de código — sem isso, não há comparação possível depois.
  2. A documentação final (um parágrafo curto, ou um comentário no código) precisa citar números reais: quantas consultas, quanto tempo, não uma descrição vaga.
  3. Confirmaremos que o resultado da versão otimizada é idêntico ao da versão original, campo a campo — não só mais rápido.
Critério de sucesso
  • ✓Existe um número de "antes" e um número de "depois", medidos com o mesmo método.
  • ✓Conferimos que o resultado da versão nova é o mesmo da antiga, não só mais rápido.
  • ✓A documentação final cita os números, não uma impressão subjetiva.

Fechando a aula

Os três temas de hoje têm uma coisa em comum: nenhum deles é sobre a IA escrever código novo — são sobre usar a IA com critério depois que o código já existe. Medir antes de confiar numa mudança, decidir com intenção quando vale coordenar mais de uma IA, e verificar o que se está conectando antes de dar acesso a algo real. É a mesma disciplina do curso inteiro — desconfiar da aparência, confirmar com evidência — aplicada a três situações novas.

De gerar código a medir se ele é bom de verdade: hoje a régua passou a ser o número, não a impressão. Otimizar com evidência, coordenar mais de uma IA com intenção, e conectar ferramentas reais com o mesmo cuidado de sempre — são as mesmas perguntas de todo o curso, agora aplicadas ao que vem depois do código pronto.
